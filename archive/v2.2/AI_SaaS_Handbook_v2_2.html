PART I: FOUNDATION

1. Introduction and Philosophy

1.1 What This Handbook Is

The AI SaaS Handbook is a complete methodology for building production-quality SaaS products using AI-assisted development. It provides structured prompts, quality gates, and verification criteria that guide you from initial idea through launch.

This is not a collection of tips. It is a system. Each stage produces artifacts that feed into subsequent stages. Vocabulary established early becomes canonical throughout. Decisions made in documentation prevent rework during implementation. Quality standards enforced at every step prevent the accumulation of technical debt that kills projects.

1.2 The Problem This Handbook Solves

AI-assisted development has a fundamental tension. AI tools can produce code faster than ever before, but speed without quality leads to disaster. A codebase full of working-but-unmaintainable code is worse than no codebase at all, because it creates the illusion of progress while accumulating hidden costs.

The handbook solves this by embedding quality requirements into every stage. Rather than building fast and fixing later, you build correctly from the start. The AI receives explicit quality criteria and verification requirements. The output is code that works AND can be maintained, extended, and debugged.

1.3 Core Principles

Documentation Before Implementation

Every hour spent on documentation saves ten hours of rework. The Business One-Pager forces clarity about what you are building and for whom. The Design Brief establishes vocabulary and constraints. The UX Package defines user flows before any code exists. The Architecture locks technical decisions before implementation begins.

Design Is Not Decoration

Good design is not about making things pretty at the end. It is about understanding users deeply, exploring multiple solutions, and making intentional choices that serve user needs. The expanded design sections in this handbook treat UX and UI as first-class concerns that receive the same rigor as architecture and code quality.

Quality Is Non-Negotiable

Every piece of code must meet explicit quality standards. Functions must be appropriately sized. Error handling must be comprehensive. Security must be defense-in-depth. Performance must be considered from the start. These are not aspirational goals. They are requirements.

Verification at Every Step

Trust but verify. AI-generated artifacts can be impressive, but they can also be subtly wrong. Every artifact produced by the handbook workflow must be verified against explicit criteria before it feeds into subsequent stages.

Right Tool for the Task

Claude Chat and Claude Code CLI have different strengths. Using the right tool for each task dramatically improves outcomes. This handbook specifies which tool to use at each stage and why.

2. The Code Quality Crisis

2.1 Understanding Vibe Coding

"Vibe coding" is a phenomenon where AI-generated code appears to work but fails to meet professional quality standards. The code passes visual inspection. It runs without errors in the happy path. But underneath, it is a maintenance nightmare waiting to happen.

The term captures the essence of the problem: the developer "goes with the vibe" rather than verifying the substance. The AI produced something that looks right, so it must be right. This assumption is dangerous.

2.2 The Six Failure Patterns

These patterns are predictable. Understanding them is the first step to preventing them.

Pattern 1: Monolithic Function Syndrome

The AI generates a single function that handles an entire feature: fetching data, transforming it, validating it, updating state, handling errors, and rendering output. This function might be 150 lines long. It technically works. But it cannot be tested in isolation, is impossible to understand at a glance, and any change risks breaking unrelated behavior.

Pattern 2: Copy-Paste Proliferation

When the AI needs similar functionality in multiple places, it often duplicates code with minor modifications rather than extracting shared logic. You end up with five slightly different implementations of the same pattern. Each has its own quirks. Bugs fixed in one place remain in the others.

Pattern 3: Implicit Coupling

The AI creates code where components know too much about each other's internals. A UI component directly accesses database logic. A utility function assumes specific application state. These hidden dependencies make the code fragile. Changes ripple unpredictably.

Pattern 4: Security Afterthought

Input validation, authentication checks, and authorization logic get added inline wherever they seem needed. There is no systematic enforcement. Some paths are protected. Others are not. The gaps are invisible until exploited.

Pattern 5: Performance Blindness

The AI generates code that works correctly but performs unnecessary operations. Data is re-fetched when it is already available. Values are re-computed on every render. Sequential API calls could be parallel. O(nÂ²) algorithms are used where O(n) is possible.

Pattern 6: Error Handling Inconsistency

Some functions have try-catch blocks. Others do not. Some errors are logged. Others are silently swallowed. Some failures show user-friendly messages. Others expose stack traces. There is no coherent strategy.

2.3 The Solution: Explicit Quality Standards

The solution is not to use AI less. It is to use AI more precisely. AI is incredibly responsive to guidance. When you provide explicit quality criteria, the AI will meet them. When you do not, the AI will optimize for what it can infer: something that looks complete.

3. The Quality Framework: Five Pillars

The quality framework provides concrete standards for evaluating code. It is organized into five pillars: Structure, Simplicity, Safety, Speed, and Stability.

3.1 Structure

Structure is about organizing code so that each piece has a clear purpose and location.

Key Principles

  • Single Responsibility: Every function, component, and module should do one thing. If you cannot describe what it does in a single sentence without "and," it is doing too much.
  • Appropriate Abstraction: Code at the same level should operate at the same abstraction level. Orchestration functions should not contain low-level details.
  • Explicit Dependencies: No reaching into global state. Dependencies come through parameters, props, or imports.
  • Cohesive Modules: Group related functionality. Separate unrelated functionality.

3.2 Simplicity

Simplicity is about minimizing cognitive load.

Key Principles

  • Function Length: Functions should rarely exceed 20-30 lines. The 100-line function is almost always a code smell.
  • Nesting Depth: Maximum 3 levels. Use early returns to reduce nesting.
  • Naming Clarity: Names should reveal intent. "userSubscriptionStatus" beats "data".
  • No Magic Values: Named constants for all numbers and strings in logic.

3.3 Safety

Safety encompasses security and correctness.

Key Principles

  • Input Validation at Boundaries: All external data validated once, at entry.
  • Defense in Depth: Multiple layers of security checks. API routes AND RLS.
  • Fail Securely: Errors should not expose sensitive information or leave inconsistent state.
  • Explicit Error Handling: Every operation that can fail should have explicit handling.

3.4 Speed

Speed is about performance and efficiency.

Key Principles

  • Avoid Unnecessary Work: Do not compute, fetch, or render what is not needed.
  • Appropriate Data Structures: Choose structures that match access patterns.
  • Database Efficiency: No N+1 queries. Select only needed columns. Use indexes.
  • Measure Before Optimizing: Profile real performance. Optimize actual bottlenecks.

3.5 Stability

Stability is about reliability and maintainability.

Key Principles

  • Test Coverage: Critical paths have automated tests.
  • Consistent Patterns: Similar problems solved similarly throughout.
  • Documentation at Decision Points: Comments explain "why" for non-obvious choices.
  • Observable Behavior: Sufficient logging and metrics for production debugging.

4. Claude Tools Guide: Chat vs Code CLI

Understanding when to use Claude Chat (web interface) versus Claude Code CLI is crucial for effective AI-assisted development. Each tool has distinct strengths, and using the right tool for each task dramatically improves outcomes.

4.1 Claude Chat (Web Interface)

Claude Chat excels at thinking, planning, and producing documents. Use it for tasks that require exploration, iteration on ideas, and producing artifacts that are primarily text-based.

Best for: Strategic thinking, document creation, design exploration, and any task where you want to discuss, iterate, and refine before committing.

Ideal Use Cases

Stage Task Why Chat Works Best
Research (0.1) Market analysis, competitive research Requires web search, iterative exploration, synthesis of multiple sources
Business One-Pager (1.0) Business strategy document Needs clarifying questions, iteration, strategic thinking
Design Brief (2.0) Single source of truth document Requires discussion, checkpoint answers, vocabulary decisions
UX Package (3.0) Wireframes, flows, states Design exploration needs conversation, multiple options, refinement
UI System (4.0) Design tokens, visual direction Visual decisions benefit from discussion and iteration
Architecture (5.0) Technical design document Complex decisions need exploration before commitment
Security (R1) Threat modeling, requirements Security analysis requires careful reasoning

Chat Workflow Tips

  • Start broad, then narrow: Begin with open exploration, then focus on specifics
  • Request multiple options: Ask for 2-3 alternatives before deciding
  • Use artifacts: Request HTML/React artifacts for interactive visualizations
  • Save outputs: Copy final documents to your project files immediately
  • Iterate in conversation: Refine outputs through follow-up questions

4.2 Claude Code CLI

Claude Code CLI excels at implementation. Use it for tasks that involve writing, modifying, and testing actual code files in your project.

Best for: Writing code, configuring infrastructure, modifying files, running commands, and any task that touches your actual codebase.

Ideal Use Cases

Stage Task Why Code CLI Works Best
Project Setup Initialize Next.js, configure tools Needs to run commands, create files, install packages
Design System Configure Tailwind, install shadcn Modifies config files, runs CLI commands
Database Create schema, migrations, RLS Writes SQL files, can test migrations
Build Implement features, components Writes code, can run and test immediately
Testing Write and run tests Needs to execute tests, see results
Debugging Find and fix issues Can read files, trace errors, apply fixes
Refactoring Improve existing code Modifies multiple files, verifies changes

Code CLI Workflow Tips

  • Provide context: Share relevant spec documents at session start
  • Work incrementally: Complete one feature before starting the next
  • Verify as you go: Run and test after each significant change
  • Commit frequently: Save working states to git often
  • Review generated code: Check against quality standards before accepting

4.3 Handoff Between Tools

The most effective workflow uses both tools, with clear handoff points.

Typical Flow

  1. Chat: Create Business One-Pager through discussion and iteration
  2. Chat: Develop Design Brief with checkpoint answers
  3. Chat: Explore UX options, create wireframes, iterate on flows
  4. Chat: Define UI system with visual direction exploration
  5. Chat: Design architecture with trade-off discussions
  6. Code CLI: Set up project infrastructure (GitHub, Supabase, Vercel)
  7. Code CLI: Implement design system configuration
  8. Code CLI: Create database schema and migrations
  9. Code CLI: Build features milestone by milestone
  10. Chat: Conduct code reviews and discuss issues
  11. Code CLI: Apply review fixes
  12. Code CLI: Final testing and deployment

Context Transfer

When moving from Chat to Code CLI, transfer context explicitly:

## Starting Code CLI Session I'm building [ProductName] and moving from planning to implementation. Key documents: - Design Brief: [paste or summarize key points] - Architecture: [paste data model and API design] - UI Specs: [paste design tokens and component list] Current milestone: [Milestone N - Name] Goal: [Specific deliverable] Quality standards to follow: - No function > 30 lines - No file > 200 lines - Zod validation on all inputs - Error handling on all async operations

Document creation Chat Benefits from conversation

PART II: DOCUMENTATION STAGES

5. Stage 0.1: Research and Opportunity Assessment

Use Claude Chat

5.1 Purpose

Before committing to build, validate that the opportunity is worth pursuing. This stage gathers market evidence, competitive intelligence, and customer signals that inform all subsequent decisions.

5.2 Quality Criteria

  • Claims must cite sources (reviews, forum posts, market reports)
  • TAM/SAM/SOM must show calculation methodology
  • Competitive analysis must include actual product testing
  • Pain points must come from real user voices
  • Go/no-go recommendation must be explicit with confidence level

5.3 Prompt Template

[ROLE: MARKET RESEARCHER - Validate opportunity for {{productName}}] CONTEXT: Evaluate whether this opportunity is worth pursuing. Be skeptical. Find evidence, not confirmation. The goal is truth, not enthusiasm. INITIAL IDEA: {{productIdea}} RULES: - Cite sources for all claims - Distinguish between evidence and assumption - Be explicit about confidence levels - Identify what would change your recommendation OUTPUT FORMAT: ## 1) MARKET SIZE - TAM: [size] - [calculation methodology] - SAM: [size] - [how narrowed] - SOM: [realistic capture] - [assumptions] ## 2) CUSTOMER PAIN EVIDENCE For each pain point: Pain, Evidence (quotes/sources), Severity ## 3) COMPETITIVE LANDSCAPE For each competitor: Name, Positioning, Strengths, Weaknesses, Pricing ## 4) POSITIONING GAP - Underserved segment, Unmet need, Evidence ## 5) KEY RISKS Risk, Likelihood, Impact, Mitigation ## 6) RECOMMENDATION - Decision: [GO / NO-GO / NEEDS MORE DATA] - Confidence: [H/M/L] - Key assumptions that must be true

6. Stage 1.0: Business One-Pager

Use Claude Chat

6.1 Purpose

The Business One-Pager forces clarity about what you are building, for whom, and why it matters. Everything downstream depends on clarity achieved here.

6.2 Required Sections

  1. Problem & Urgency - What specific problem? Why painful enough to pay?
  2. Ideal Customer Profile - Who specifically? Where do they congregate?
  3. Solution - What does it do? What does it NOT do?
  4. Differentiation - Why choose this over alternatives?
  5. Revenue Model + Pricing - How make money? Pricing structure?
  6. #1 Money Action - Single measurable revenue-generating action
  7. MVP Scope - Must-have for v1. Explicit exclusions.
  8. Key Risks - What could kill this? Validation plan?
  9. Success Metrics - Activation, retention, conversion targets

Verification Checklist

  1. All nine sections present and substantive
  2. ICP specific enough to identify real people
  3. Success metrics have specific numeric targets
  4. MVP scope has explicit inclusions AND exclusions
  5. Assumptions marked with [ASSUMPTION] label

7. Stage 2.0: Shared Design Brief

Use Claude Chat

7.1 Purpose

The Design Brief is the single source of truth for all subsequent work. Vocabulary defined here becomes canonical. Every subsequent prompt receives this document verbatim.

7.2 Required Sections

  1. SaaS One-Liner - "[Product] helps [ICP] to [outcome] by [mechanism]"
  2. Target Users - Primary persona, context, current pain
  3. #1 Money Action - "[User] [verbs] [object]"
  4. Top 3 Jobs To Be Done - JTBD format
  5. MVP Screens/Pages - Every screen with purpose
  6. Core User Journey - 6-10 steps
  7. Constraints - Stack, deadline, must-keep
  8. Competitors/Inspirations - Copy this, avoid that
  9. Success Metrics - Targets with numbers
  10. Checkpoint Answers - All architectural decisions

7.3 Checkpoint Questions

Every question must have an explicit answer - no "TBD" allowed:

  • Tenancy: single-user | single-workspace | multi-workspace
  • Roles: owner-only | owner+member | owner+admin+member+viewer
  • Billing: seat-based | usage-based | flat-rate + trial | freemium | paid
  • Activation moment: what happens in first 5 minutes
  • Core entities: top 3 data objects
  • Integrations: required for MVP
  • Day-1 emails: magic-link, welcome, invite, receipt (y/n each)
  • File uploads: y/n, types, max size
  • Background jobs: y/n, what kind
  • Audit trail: y/n
  • Data export: y/n, format
  • Support: contact-form | chat | email
  • Compliance: none | GDPR | SOC2-later

PART III: DESIGN EXCELLENCE

8. Design Philosophy and Process

Good design is not decoration applied at the end. It is a process of deeply understanding user needs, exploring multiple solutions, and making intentional choices that serve those needs. This section establishes the design philosophy that guides all UX and UI work in the handbook.

8.1 Design Principles

User-Centered, Not Feature-Centered

Every design decision should trace back to a user need. "Users need to quickly understand their subscription status" is a valid driver. "We should add a dashboard widget" is not. Start with jobs to be done, not features to build.

Clarity Over Cleverness

The best interfaces are invisible. Users should accomplish their goals without thinking about the interface. Resist the temptation to add visual flourishes that do not serve comprehension. Every element should earn its place.

Consistency Creates Confidence

When patterns are consistent, users learn the interface once and can predict behavior. Inconsistency forces users to relearn, creates confusion, and erodes trust. Establish patterns early and apply them rigorously.

Design for the Edges

Empty states, error states, and edge cases are not afterthoughts. They are often the moments of highest user frustration or opportunity. Design these states with as much care as the happy path.

Accessibility Is Not Optional

Accessible design is better design for everyone. Sufficient contrast, keyboard navigation, screen reader support, and touch-friendly targets improve the experience for all users, not just those with disabilities.

8.2 The Design Process

The handbook design process has four phases, each building on the previous:

Phase 1: Understand (Part of Design Brief)

Define who users are, what they need to accomplish, and what constraints exist. This happens primarily in the Design Brief through persona definition, jobs to be done, and checkpoint questions.

Phase 2: Explore (UX Package)

Generate multiple approaches to solving user needs. Create wireframes for different layouts and flows. Do not commit to a single direction too early. Exploration prevents premature optimization.

Phase 3: Refine (UX Critic + UI System)

Critique the explorations rigorously. Identify friction, gaps, and inconsistencies. Then translate the refined UX into a visual system with multiple direction options before selecting one.

Phase 4: Specify (Final UI Specs)

Document the chosen direction with enough detail for implementation. Design tokens, component specifications, screen-by-screen breakdowns, and interaction details.

8.3 Multiple Options Requirement

Critical: At key decision points, you must generate multiple options before committing. A single option is not a choice - it is a default. Choices require alternatives.

Specifically, require multiple options for:

  • Information Architecture: 2-3 different ways to organize navigation and screens
  • Core Flow Layout: 2-3 different layouts for the main user journey
  • Visual Direction: 3 distinct visual approaches before selecting one
  • Complex Interactions: 2+ approaches for any non-trivial interaction

Database migrations flow from local to dev to production, never the reverse. This ensures that production always receives tested, verified schema changes.

Appendix B: Anti-Pattern Reference

Structure Anti-Patterns

  • Deep Nesting: 4+ levels. Fix: Early returns, extract helpers.
  • Implicit Dependencies: Hidden globals. Fix: Pass as parameters.

Safety Anti-Patterns

  • Optimistic Trust: Assuming valid input. Fix: Validate at boundaries.

  • Security Sprinkle: Random auth checks. Fix: Consistent boundaries.

Performance Anti-Patterns

  • N+1 Queries: Loop fetching. Fix: Joins or batch fetches.
  • Render Thrashing: Constant re-renders. Fix: Memoization.
  • Eager Loading: Everything upfront. Fix: Lazy loading.
