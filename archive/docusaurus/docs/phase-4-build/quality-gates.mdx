## What are Quality Gates?

Quality gates are mandatory checkpoints that verify your code meets defined standards before proceeding. Every item must pass—no exceptions, no "we'll fix it later."

:::info Gate Philosophy
Quality gates exist because **technical debt compounds**. A small shortcut in M1 becomes a significant problem in M6. Gates force you to address issues when they're cheap to fix.
:::

## SPEC Ready Gate

Before starting implementation, verify the SPEC meets these criteria:

| Criteria | Verification |
|----------|--------------|
| Overview section complete | Problem and Solution clearly stated |
| Build Contract references included | Section numbers cited |
| At least one requirement (EARS format) | Follows pattern correctly |
| At least one test case per requirement | GIVEN-WHEN-THEN format |
| All placeholders replaced | No `[PLACEHOLDER]` text remains |
| Status set to "Ready" | Marked for implementation |

## Implementation Done Gate

Before marking a feature complete, verify these criteria:

```bash
# All tests must pass
npm test

# No TypeScript errors
npm run build

# No linting errors
npm run lint

# Check for security vulnerabilities
npm audit
```

| Criteria | Threshold |
|----------|-----------|
| Tests pass | 100% |
| Test coverage for new code | ≥ 80% |
| Functions | ≤ 30 lines |
| Files | ≤ 200 lines |
| Nesting depth | ≤ 3 levels |
| TypeScript errors | 0 |
| Linting errors | 0 |
| SPEC status | Updated to "Done" |

### Checkpoint 1: Foundation Audit

After completing M1-M4, verify:

| Criteria | Verification Method |
|----------|---------------------|
| RLS enabled on ALL tables | Query pg_tables for rowsecurity |
| RLS policies tested | Attempt unauthorized access (should fail) |
| No security vulnerabilities | `npm audit` clean |
| Schema matches architecture | Compare to data model doc |
| Technical debt score | ≥ 6.0 |
| All M1-M4 tests passing | `npm test` |
| Git tagged | `checkpoint-1` |

## Code Review Gate

Before merging any PR:

| Criteria | Check |
|----------|-------|
| PR linked to SPEC | Reference included |
| Tests cover new functionality | Coverage verified |
| No console.log statements | Search codebase |
| No hardcoded secrets | Review for credentials |
| Error handling in place | Try/catch, error boundaries |
| TypeScript types defined | No `any` types |
| Follows project conventions | CLAUDE.md rules followed |
| Documentation updated | If API or usage changed |

## Quality Score Thresholds

| Score | Rating | Gate Decision |
|-------|--------|---------------|
| ≥ 8.0 | Excellent | **PASS** — Proceed |
| 7.0 - 7.9 | Good | **PASS** — Document debt |
| 6.0 - 6.9 | Acceptable | **PASS** — Create remediation plan |
| 5.0 - 5.9 | Concerning | **CONDITIONAL** — Address before next milestone |
| < 5.0 | Critical | **BLOCK** — Remediation required |

## Using Quality Gates

### Manual Verification

Copy the relevant checklist into your SPEC or PR description and check off items:

```markdown
## Quality Gate: Implementation Done

- [x] All tests pass (npm test)
- [x] Test coverage >= 80%
- [x] Functions <= 30 lines
- [x] Files <= 200 lines
- [x] No TypeScript errors (npm run build)
- [x] No linting errors (npm run lint)
- [ ] SPEC status updated to "Done"
```

### Automated Verification

Many checks can be automated via CI/CD:

```yaml
# .github/workflows/quality-gate.yml
name: Quality Gate

on: [pull_request]

jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install dependencies
        run: npm ci

      - name: Run tests
        run: npm test -- --coverage

      - name: Check coverage threshold
        run: npm run test:coverage -- --coverageThreshold='{"global":{"branches":80,"functions":80,"lines":80}}'

      - name: Type check
        run: npm run build

      - name: Lint
        run: npm run lint

      - name: Security audit
        run: npm audit --audit-level=high
```

## Common Gate Failures

| Failure | Root Cause | Solution |
|---------|------------|----------|
| Tests failing | Incomplete implementation | Complete TDD cycle |
| Low coverage | Tests not written first | Write tests before code |
| TypeScript errors | Missing types | Add proper type definitions |
| Lint errors | Style violations | Run `npm run lint -- --fix` |
| Large functions | Over-engineering | Extract to smaller functions |
| Security vulnerabilities | Outdated packages | Update dependencies |
