## Why Write SPECs Before Code?

A **SPEC** (Specification Document) defines what a feature should do before writing any code. Every feature, no matter how small, starts with a SPEC.

:::warning The SPEC-First approach prevents the most common failure mode in AI-assisted development
Without a SPEC, AI tends to:
- Make assumptions about requirements that seem reasonable but are incorrect
- Generate code that works but doesn't match what you actually need
- Create implementations that are hard to verify because requirements were never explicit

With a SPEC:
- Requirements are explicit and verifiable
- Test cases are defined before implementation
- Acceptance criteria are clear
- Claude Code has precise context for implementation

**The extra 10-15 minutes spent writing a SPEC typically saves hours of debugging and rework.**
:::

## EARS Requirements Format

EARS (Easy Approach to Requirements Syntax) provides five patterns for writing unambiguous requirements. Using these patterns ensures your requirements are testable and clear.

| Type | Pattern | Example |
|------|---------|---------|
| **Ubiquitous** | The [system] shall [action] | The upload zone shall accept JPEG, PNG, and HEIC formats. |
| **State-Driven** | While [state], the [system] shall [action] | While uploading, the system shall display progress. |
| **Event-Driven** | When [event], the [system] shall [action] | When user clicks generate, the system shall call the AI API. |
| **Optional** | Where [condition], the [system] shall [action] | Where user is Pro tier, the system shall enable all styles. |
| **Unwanted** | The [system] shall not [action] | The system shall not store raw API keys. |

### Examples by Type

**Ubiquitous** — Always true, no conditions:
```
REQ-AUTH-001: The system shall hash passwords using bcrypt with cost factor 12.
REQ-AUTH-002: The login form shall require both email and password fields.
```

**State-Driven** — Depends on current state:
```
REQ-UPLOAD-001: While a file is uploading, the system shall display a progress bar.
REQ-SESSION-001: While the user is authenticated, the system shall refresh tokens every 55 minutes.
```

**Event-Driven** — Triggered by an action:
```
REQ-AUTH-003: When the user submits valid credentials, the system shall create a session.
REQ-UPLOAD-002: When upload completes, the system shall display a success notification.
```

**Optional** — Conditional based on context:
```
REQ-BILLING-001: Where user has Pro subscription, the system shall allow unlimited uploads.
REQ-ADMIN-001: Where user has admin role, the system shall display the admin menu.
```

**Unwanted** — Explicitly prohibited:
```
REQ-SEC-001: The system shall not log password values.
REQ-SEC-002: The system shall not expose internal error details to users.
```

## Test Case Format

Test cases use the GIVEN-WHEN-THEN format, which clearly separates preconditions, actions, and expected outcomes. This format maps directly to test code structure.

```markdown
### TC-PHOTO-001: Valid image upload

**GIVEN** a user is on the create listing page
  AND the user has selected a valid JPEG image
**WHEN** the user drops the image on the upload zone
**THEN** the system displays an upload progress indicator
  AND the image appears in the preview grid after upload completes
```

### Test Case Best Practices

1. **One scenario per test case** — Don't combine multiple scenarios
2. **Specific values** — Use concrete examples, not vague descriptions
3. **Testable assertions** — Every THEN must be verifiable
4. **Cover edge cases** — Include error scenarios and boundary conditions

### Example SPEC Document

```markdown
# SPEC-AUTH-001: User Login

## Overview

**Problem:** Users need to securely access their accounts.
**Solution:** Email/password login with session management.
**Build Contract Reference:** Section 2.3 Authentication

## Requirements

### REQ-AUTH-001 (Ubiquitous)
The login form shall require email and password fields.

### REQ-AUTH-002 (Event-Driven)
When the user submits valid credentials, the system shall create
a session and redirect to the dashboard.

### REQ-AUTH-003 (Event-Driven)
When the user submits invalid credentials, the system shall display
an error message without revealing which field was incorrect.

### REQ-AUTH-004 (Unwanted)
The system shall not log password values in any form.

## Test Cases

### TC-AUTH-001: Successful login
**GIVEN** a registered user with email "test@example.com"
  AND password "SecurePass123!"
**WHEN** the user enters these credentials and clicks login
**THEN** the system creates a session
  AND redirects to /dashboard
  AND displays the user's name in the header

### TC-AUTH-002: Invalid password
**GIVEN** a registered user with email "test@example.com"
**WHEN** the user enters correct email but wrong password
**THEN** the system displays "Invalid email or password"
  AND does not create a session
  AND login form remains displayed

### TC-AUTH-003: Unregistered email
**GIVEN** no user with email "unknown@example.com" exists
**WHEN** the user attempts to login with this email
**THEN** the system displays "Invalid email or password"
  AND response time is similar to valid email (timing attack prevention)

## Acceptance Criteria
- [ ] All test cases pass
- [ ] No password values in logs
- [ ] Session expires after 24 hours of inactivity
- [ ] Login works on mobile and desktop
```

## Action Steps

1. **Write SPECs before coding** — For each feature, create a SPEC document in `docs/specs/` using the template
2. **Use EARS format for requirements** — Every requirement must follow one of the five EARS patterns
3. **Create test cases for each requirement** — At minimum, one test case per requirement; complex requirements may need multiple
4. **Reference Build Contract sections** — Each SPEC must cite the relevant Build Contract sections it implements

### Manual Steps

```bash
# Create a new SPEC file
touch docs/specs/SPEC-AUTH-001.md

# Copy the template and customize
# Ensure all [PLACEHOLDER] values are replaced
```

### With Claude Code

```bash
claude "Create SPEC-AUTH-001 for user login using the template in docs/specs/
Reference Build Contract section 2.3 for authentication requirements"
```
