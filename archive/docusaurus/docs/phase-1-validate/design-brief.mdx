## What is a Design Brief?

A Design Brief bridges business strategy and product design. It captures the **"what"** without prescribing the **"how"**. Think of it as the handoff document from business planning to UX/UI design.

The Design Brief answers:
- What features are we building?
- Who are we building them for?
- How will we know when each feature is complete?

:::info Design Brief vs PRD vs SPEC
**Design Brief** (this chapter): High-level features and user stories. Written in Claude Chat or manually.

**PRD (Product Requirements Document)**: More detailed, often includes wireframes. We fold this into the UX Package in Phase 2.

**SPEC Document**: Implementation-level detail for Claude Code. Created per-feature in Phase 4.
:::

## Design Brief Structure

Your Design Brief should include these sections:

### 1. Product Overview

A single paragraph summarizing what you're building and why. This should be derived from your Business One-Pager.

```markdown
## Product Overview

[Product Name] is a [category] that helps [target user] to [core value proposition].
Unlike [competitor/alternative], our product [key differentiator].
```

### 2. Target User Personas

Brief descriptions of your primary user types. Keep this to 2-3 personas maximum for MVP.

| Persona | Description | Primary Need |
|---------|-------------|--------------|
| Persona 1 | Brief description | What they need most |
| Persona 2 | Brief description | What they need most |

### 3. Core Features (MVP)

List 3-5 features for your MVP. Each feature should include:
- **Feature Name**: Clear, concise identifier
- **Description**: What the feature does (1-2 sentences)
- **User Stories**: 2-4 stories in "As a [user], I want [goal] so that [benefit]" format
- **Acceptance Criteria**: Testable conditions for "done"

### 4. Out of Scope

Explicitly list features you are **not** building in the MVP. This prevents scope creep and sets stakeholder expectations.

### 5. Success Metrics

How will you measure if the MVP is successful? Include 2-3 measurable metrics.

Follow these steps to complete your Design Brief:

### Step 1: Copy the Template

```bash

```

### Step 2: Fill in Product Overview

Use your Business One-Pager as the source. Keep it to one paragraph.

### Step 3: Define User Personas

Review your Market Research and Opportunity Assessment. Extract the 2-3 most important user types.

### Step 4: Document Core Features

This is the most important section. For each feature:

1. Write a clear feature name and description
2. Create 2-4 user stories
3. Define testable acceptance criteria

## Example: Design Brief Excerpt

Here's a partial example for a task management app:

```markdown
## Core Feature: Task Creation

**Description:** Users can create tasks with a title, description, due date, and priority level.

### User Stories

1. As a user, I want to quickly create a task with just a title so that I can capture ideas without friction.

2. As a user, I want to set a due date on my task so that I can track deadlines.

3. As a user, I want to assign a priority (High/Medium/Low) so that I can focus on what matters most.

### Acceptance Criteria

- [ ] User can create a task with title only (minimum required field)
- [ ] Title has 200 character maximum with validation
- [ ] Due date picker shows calendar UI
- [ ] Due date cannot be in the past
- [ ] Priority defaults to "Medium" if not specified
- [ ] Task appears in list immediately after creation
- [ ] Success toast confirms task creation
```

## Common Mistakes to Avoid

1. **Too many features**: Stick to 3-5 for MVP
2. **Vague user stories**: Every story should have a clear "so that" benefit
3. **Untestable acceptance criteria**: If you can't test it, rewrite it
4. **Missing "Out of Scope"**: This prevents scope creep later
5. **No success metrics**: You need to know what "done" looks like
