## What is a UX Package?

The UX Package defines the **complete user experience**: all screens, all flows, all states. It answers every question a developer might have about "what happens when..." scenarios.

:::warning The Most Common Design Failure
Building without a UX Package leads to discovering edge cases during development. Each discovery costs hours of rework. A complete UX Package upfront prevents this.
:::

## UX Package Structure

Your UX Package should include five sections:

### Section 1: Information Architecture

The complete structure of your application:

- **Site Map**: All screens/routes in your application
- **Navigation Structure**: How users move between areas
- **User Flow Diagrams**: Visual paths through key journeys

### Section 2: Screen Inventory

For **every screen** in your application, document:

| Element | Description |
|---------|-------------|
| Screen Name | Clear identifier |
| Route | URL path (e.g., `/dashboard`, `/settings`) |
| Purpose | What user accomplishes here |
| Entry Points | How user arrives at this screen |
| Exit Points | Where user goes next |
| Key Components | Major UI elements on screen |
| Data Displayed | What information is shown |
| Data Collected | What user inputs |
| Actions Available | Buttons, links, interactions |
| Loading State | What shows while data loads |
| Empty State | What shows when no data exists |
| Error State | What shows when something fails |

### Section 3: User Flows

For each core flow from your Design Brief:

- Step-by-step sequence
- Decision points and branches
- Error recovery paths
- Success confirmation

### Section 4: Component Behaviors

Interaction patterns used across the app:

- **Form Validation**: When and how validation runs
- **Confirmation Dialogs**: When to confirm and wording
- **Notifications**: Types, duration, dismissal
- **Loading Indicators**: Spinners, skeletons, progress bars

### Section 5: Responsive Behavior

- Breakpoints (e.g., mobile < 768px, tablet < 1024px)
- What changes at each breakpoint
- Mobile-specific interactions (swipe, tap targets)

## Example: Screen Inventory Entry

```markdown
### Dashboard Screen

**Route**: `/dashboard`
**Purpose**: Give user overview of their account and quick actions

**Entry Points**:
- Login success
- Logo click from any screen
- "Dashboard" nav item

**Exit Points**:
- Create new [item] → /items/new
- View [item] → /items/:id
- Settings → /settings

**Key Components**:
- Header with navigation
- Stats summary cards (3)
- Recent activity list
- Quick action buttons

**Data Displayed**:
- Total [items] count
- This month's [metric]
- Recent 5 [items]

**Actions Available**:
- Create new [item]
- View [item] details
- Filter activity

**Loading State**: Skeleton cards, skeleton list
**Empty State**: "Welcome! Create your first [item] to get started" + CTA
**Error State**: "Unable to load dashboard. Retry?" + Retry button
```

## Validation Checklist

Before moving on, ensure your UX Package passes these checks:

| Check | What to Verify |
|-------|----------------|
| Screen Count | Typical MVP has 8-15 screens |
| All States | Every screen has loading, empty, error states |
| Entry/Exit | Every screen has defined entry and exit points |
| Flow Coverage | All core flows from Design Brief are documented |
| Edge Cases | Common edge cases addressed (first-time user, returning user, admin) |
