PART I: FOUNDATION

Philosophy, Quality Framework, and Tool Selection

Chapter 1: Introduction and Philosophy

1.1 The Vision

This handbook presents a methodology for building production-quality SaaS products using AI-assisted development. The goal is not just working code, but code that is secure, maintainable, testable, and ready for scale.

Version 3.0 introduces MOAI-ADK integration, which transforms the Build Phase from a series of prompts into a disciplined, test-driven development process where every feature begins with a specification and ends with verified, documented code.

The MOAI Principle

Specification Before Implementation. Every feature, no matter how small, starts with a SPEC that defines requirements, test cases, and acceptance criteria. Implementation follows the TDD cycle: write failing tests (RED), implement to pass (GREEN), improve code quality (REFACTOR).

Chapter 2: The Quality Framework

2.1 Five Pillars of Quality

Every piece of code produced through this methodology must meet standards across five dimensions:

Pillar 1: Correctness

  • Code does what the SPEC says it should do
  • All test cases pass
  • Edge cases are handled
  • Error conditions produce appropriate responses

Pillar 2: Security

  • Authentication required on protected routes
  • Authorization checks on data access
  • Input validation on all user data
  • Parameterized queries (no SQL injection)
  • No sensitive data in logs or responses

Pillar 3: Maintainability

  • Functions under 30 lines
  • Files under 200 lines
  • Nesting under 3 levels
  • Clear naming conventions
  • Consistent code style

Pillar 4: Testability

  • Minimum 80% test coverage
  • Unit tests for business logic
  • Integration tests for API routes
  • Tests follow GIVEN-WHEN-THEN format

Pillar 5: Documentation

  • SPEC documents requirements
  • Code comments explain "why" not "what"
  • README files for major components
  • API documentation maintained

2.2 Quality Gate Definitions

SPEC Quality Gate (Before Implementation)

  • At least one requirement defined
  • Each requirement has at least one test case
  • Requirements use EARS format
  • Test cases use GIVEN-WHEN-THEN format
  • Build Contract sections referenced
  • Acceptance criteria defined

Implementation Quality Gate (After Implementation)

  • All test cases pass
  • Code meets structure standards
  • Security checks present
  • No TypeScript errors
  • Linting passes

PART IV-B: BUILD CONTRACT NEW IN v3.0

Bridging Design to Implementation

Chapter 20: Build Contract Introduction

20.1 What is a Build Contract?

The Build Contract is a bridge document that compresses your design artifacts (Design Brief, UX Package, UI System, Architecture) into a structured reference optimized for implementation. It serves as the authoritative source of truth during the Build Phase.

Why Build Contract?

Design artifacts are optimized for exploration and decision-making. But during implementation, you need quick reference to decisions made, not the journey to get there.

The Build Contract extracts the "what" from design artifacts and organizes it for implementation lookup. SPECs reference Build Contract sections rather than hunting through multiple design documents.

20.2 Build Contract Benefits

Without Build Contract With Build Contract
SPECs reference multiple documents SPECs reference single source
Context window filled with full design docs Context window uses compressed reference
~15-20K tokens for design context ~2-5K tokens for relevant sections

Chapter 21: Build Contract Structure

21.1 Standard Sections

Every Build Contract contains seven standard sections:

Section 1: Vocabulary

Canonical terms used throughout the product. Extracted from Design Brief.

Section 2: User Model

User types, permissions, authentication, and core flows. Extracted from UX Package.

Section 3: Screen Inventory

Complete list of screens with routes and key components. Extracted from UI System.

Section 4: Component Specifications

Key component behaviors, states, and validation rules. Extracted from UI System.

Section 5: Data Model

Database entities, columns, types, constraints, and relationships. Extracted from Architecture.

Section 6: API Surface

All API routes with methods, purposes, and auth requirements. Extracted from Architecture.

Section 7: Quality Standards

Code structure, security, testing, and performance requirements. Compiled from all documents.

Chapter 25: SPEC-First Development

25.1 What is a SPEC?

A SPEC (Specification) is a document that fully defines a feature before implementation begins. It contains:

  • Overview: What problem does this feature solve?
  • Source References: Which Build Contract sections are relevant?
  • Requirements: What must the feature do? (EARS format)
  • Test Cases: How do we verify each requirement? (GIVEN-WHEN-THEN)
  • Acceptance Criteria: When is this feature "done"?

25.2 SPEC Identification

SPEC-[PREFIX]-[NUMBER] Examples: - SPEC-PHOTO-001: Photo upload functionality - SPEC-AUTH-001: User authentication - SPEC-GEN-001: Description generation - SPEC-DASH-001: Dashboard display

25.3 EARS Requirements Format

Type Pattern Example
Ubiquitous The [system] shall [action] The upload zone shall accept JPEG, PNG, and HEIC formats.
State-Driven While [state], the [system] shall [action] While photos are uploading, the system shall display a progress indicator.
Event-Driven When [event], the [system] shall [action] When user clicks generate, the system shall call the AI API.
Optional Where [condition], the [system] shall [action] Where user is Pro tier, the system shall enable all styles.
Unwanted The [system] shall not [action] The system shall not store raw API keys in the database.

25.4 Test Case Format

### TC-PHOTO-001: Valid image upload **GIVEN** a user is on the create listing page AND the user has selected a valid JPEG image (1920x1080) **WHEN** the user drops the image on the upload zone **THEN** the system displays an upload progress indicator AND the image appears in the preview grid after upload completes AND the photo count increases by 1

Chapter 26: TDD Workflow

26.1 The RED-GREEN-REFACTOR Cycle

TDD CYCLE ========= +--------+ | RED | Write failing tests from SPEC test cases +---+----+ | v +--------+ | GREEN | Write minimum code to pass tests +---+----+ | v +----------+ | REFACTOR | Improve code quality, tests still pass +----+-----+ | v +--------+ | DONE | All tests pass, quality gate passed +--------+

26.2 RED Phase: Write Failing Tests

Claude Code Prompt - RED Phase: I'm implementing SPEC-PHOTO-001: Photo Upload Functionality. Here is the SPEC: [Paste SPEC content] Please write the test file(s) for this SPEC. Follow these rules: 1. Create test file at: src/__tests__/[feature]/[spec-id].test.ts 2. Write one test for each TC- test case in the SPEC 3. Use GIVEN-WHEN-THEN as comments within each test 4. Tests should fail initially (implementation doesn't exist) 5. Use Jest/Vitest testing framework After writing tests, run them to confirm they fail as expected.

26.3 GREEN Phase: Implement to Pass

Claude Code Prompt - GREEN Phase: The tests for SPEC-PHOTO-001 are written and failing as expected. Please implement the minimum code to make all tests pass. Follow these rules: 1. Focus only on passing tests, not on code elegance 2. Reference Build Contract sections mentioned in SPEC 3. Run tests after each significant code addition 4. Stop as soon as all tests pass Do not refactor or optimize during this phase.

26.4 REFACTOR Phase: Improve Quality

Claude Code Prompt - REFACTOR Phase: All tests for SPEC-PHOTO-001 are passing. Please refactor the implementation to meet quality standards: 1. Functions under 30 lines 2. Files under 200 lines 3. Nesting under 3 levels 4. Clear naming conventions 5. Extract reusable utilities 6. Add appropriate error handling Run tests after each refactoring change to ensure they still pass.

Chapter 29: Checkpoint Procedures

29.1 Checkpoint A: Code Audit

Checkpoint A Requirements (After M5, Before M6)

Automated Checks:

  • All tests passing
  • Test coverage >= 80%
  • No TypeScript errors
  • Linting clean
  • No security vulnerabilities in dependencies

Manual Review:

  • Authentication flow works end-to-end
  • Database schema matches Build Contract
  • RLS policies correctly restrict access
  • Error handling is consistent

29.2 Checkpoint B: Feature Complete

Checkpoint B Requirements (After M6, Before M7)

Automated Checks:

  • All tests passing
  • Test coverage >= 80%
  • Performance benchmarks met

Manual Review:

  • Core feature works end-to-end
  • All user flows from UX Package functional
  • Error states handled gracefully
  • Loading states provide feedback

User Testing:

  • At least one person besides developer tests core flow
  • Feedback documented and triaged
