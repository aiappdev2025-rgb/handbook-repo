PART I: FOUNDATION

In this chapter, you'll learn the philosophy behind structured prompts and how to use this guide effectively. By the end, you'll understand the six-section prompt pattern, how to customize prompts for your project, and the milestone-based approach to building your SaaS.

1.1 Introduction: Why Structured Prompts Matter

Understanding why structured prompts work better than free-form instructions is essential for getting consistent, high-quality results from AI assistance.

Long, dense prompts fail for three predictable reasons. First, when too many requirements compete for attention, the AI loses focus on what matters most. Second, important details get buried in walls of text and get skipped. Third, without clear structure, the AI fills gaps with assumptions that may not match what you actually need.

This guide restructures the Build phase into clear, focused prompts that follow a consistent format. Each prompt is organized into labeled sections that are easy to scan. Each milestone includes explicit checkpoints for code quality, security, and functionality.

1.2 The Prompt Structure Philosophy

The six-section pattern creates consistency across all prompts, making them easier to use and more reliable in their outputs.

Every prompt in this guide follows the same six-section pattern, making them predictable and easy to work with.

ROLE establishes who the AI should act as. This grounds the AI in the right mindset before diving into specifics. A "Senior Full-Stack Developer" approaches problems differently than a "Junior Developer learning the ropes."

CONTEXT describes what exists right now. What files are in place. What has been completed in previous milestones. This prevents the AI from making incorrect assumptions about starting conditions, which is one of the most common sources of errors.

OBJECTIVE states the specific goal for this prompt. One clear objective per prompt. If you have multiple objectives, split them into multiple prompts. This focus is essential for quality output.

REQUIREMENTS provides detailed specifications organized by category. Functional requirements, quality requirements, and constraints are all separated so nothing gets lost. Each requirement is a separate line item that can be checked off.

QUALITY STANDARDS defines what "good" looks like. This is where the anti-vibe-coding safeguards live. Without explicit quality criteria, the AI optimizes for "looks complete" rather than "is maintainable."

DELIVERABLES & VERIFICATION specifies exactly what files should be produced and how to confirm the work is complete. This creates accountability and makes it easy to know when you're done.

1.3 How to Edit and Customize Prompts

Effective prompt customization is the difference between getting generic code and getting code tailored to your specific project needs.

Every prompt in this guide contains placeholders that you must customize for your specific project. Understanding what to change and what to keep is essential for getting good results.

Understanding Placeholders

Placeholders appear in two formats throughout the prompts:

  • [BRACKET PLACEHOLDERS] - Replace the entire bracket with your specific value. Example: [PRODUCT NAME] becomes PhotoListPro
  • {{DOUBLE BRACE PLACEHOLDERS}} - Indicates where to paste actual content like code files. Example: {{paste your schema here}}

What to Customize

Always Replace:
  • [PRODUCT NAME] - Your actual product name
  • [YOUR BUSINESS LOGIC] - Specific features and rules for your app
  • [TABLE NAMES] - Your actual database table names from your schema
  • [YOUR ENTITY] - The main object your app works with (listings, invoices, projects, etc.)
  • {{paste code here}} - Actual code from your project

What to Keep Unchanged

Do Not Modify:
  • QUALITY STANDARDS section - These enforce code quality and prevent vibe coding
  • ROLE definitions - These set the right expertise level
  • Security requirements - RLS policies, input validation, auth checks
  • File structure conventions - Consistent organization aids maintainability

Example: Customizing a Prompt

Original prompt text:

CONTEXT This is [PRODUCT NAME], a [DESCRIPTION]. The core entity is [YOUR ENTITY] stored in the [TABLE NAME] table.

Customized for a real estate listing app:

CONTEXT This is PhotoListPro, a real estate listing description generator. The core entity is "listing" stored in the listings table.

When to Split Prompts

If a prompt becomes too long or complex after customization (over ~2000 words), split it into multiple focused prompts. Complete and verify each part before moving on.

Manual vs Claude Code Execution

Most prompts in this guide can be executed two ways:

Method When to Use How
Claude Code CLI You have Claude Code installed and configured with CLAUDE.md Copy prompt, run claude in terminal, paste prompt
Manual Execution No Claude Code, or prefer manual control Copy prompt to Claude Chat, manually create files from the output

For manual execution, after Claude generates code, you'll need to:

  1. Create the specified files in your project
  2. Copy the generated code into each file
  3. Run the verification steps yourself (npm run build, npm test, etc.)
  4. Fix any issues Claude identifies before proceeding

Major Checkpoints

In addition to per-milestone quality gates, there are three major checkpoints where you pause for deeper review. Each checkpoint includes mandatory security verification.

Checkpoint A: After Milestone 3 (Database)

Before building features, verify the data foundation is solid. Review schema design. Confirm all RLS policies are in place. Test that policies actually work by attempting unauthorized access. This includes the admin tables if you're building the admin console.

Security Requirements for Checkpoint A:

  • ✓ RLS enabled on ALL tables (no exceptions)
  • ✓ Every table has SELECT policy restricting to owner or admin
  • ✓ INSERT/UPDATE/DELETE policies verify user owns the record
  • ✓ Test as anon role: SET LOCAL ROLE anon; SELECT * FROM [table]; — should fail
  • ✓ Test as wrong user: Verify User A cannot access User B's data
  • ✓ No service_role key in any client-side code

Checkpoint B: After Milestone 7 (Admin Console)

The admin console provides your operational visibility. Verify you can find and view any user, see subscription statuses, and access error logs. Test admin role restrictions to ensure non-admins cannot access admin routes. This is your last checkpoint before building additional user-facing features.

Security Requirements for Checkpoint B:

  • ✓ Run the Security Audit Prompt (Part V of this guide)
  • ✓ Non-admin users redirected from /admin routes (test in browser)
  • ✓ Admin actions logged to admin_audit_logs table
  • ✓ All API routes have Zod input validation
  • ✓ All forms validate input client-side AND server-side
  • ✓ No hardcoded secrets in codebase: grep -r "secret\|password\|key" src/
  • ✓ XSS test: Enter <script>alert(1)</script> in text fields — must be escaped
  • ✓ npm audit shows no high/critical vulnerabilities

Checkpoint C: After Milestone 10 (Polish)

Before final testing, ensure the codebase is clean. Run the full refactoring audit. Address all accumulated technical debt. Verify error handling is comprehensive. Confirm all states are handled in the UI.

Security Requirements for Checkpoint C:

  • ✓ Run the Security Audit Prompt again (final verification)
  • ✓ Security headers configured in next.config.js (HSTS, X-Frame-Options, etc.)
  • ✓ Error messages don't expose sensitive information
  • ✓ Rate limiting on login, signup, password reset, and payment endpoints
  • ✓ All environment variables documented in .env.example (without values)
  • ✓ .gitignore includes .env, .env.local, .env.*.local
  • ✓ No console.log statements with sensitive data: grep -r "console.log" src/ | grep -i "password\|token\|secret"

-- Helper function to check if current user is admin CREATE OR REPLACE FUNCTION public.is_admin() RETURNS boolean AS $$ BEGIN RETURN EXISTS ( SELECT 1 FROM public.profiles WHERE id = auth.uid() AND role IN ('admin', 'super_admin') ); END; $$ LANGUAGE plpgsql SECURITY DEFINER; -- Helper function to check if current user is super admin CREATE OR REPLACE FUNCTION public.is_super_admin() RETURNS boolean AS $$ BEGIN RETURN EXISTS ( SELECT 1 FROM public.profiles WHERE id = auth.uid() AND role = 'super_admin' ); END; $$ LANGUAGE plpgsql SECURITY DEFINER;

B.6 RLS Policies

Row Level Security policies that control access to admin tables based on user roles.

-- Admin audit logs: admins can read, system inserts ALTER TABLE public.admin_audit_logs ENABLE ROW LEVEL SECURITY; CREATE POLICY "Admins can view audit logs" ON public.admin_audit_logs FOR SELECT USING (public.is_admin()); -- Admin notes: admins can CRUD ALTER TABLE public.admin_notes ENABLE ROW LEVEL SECURITY; CREATE POLICY "Admins can manage notes" ON public.admin_notes FOR ALL USING (public.is_admin()); -- System settings: admins read, super_admins write ALTER TABLE public.system_settings ENABLE ROW LEVEL SECURITY; CREATE POLICY "Admins can view settings" ON public.system_settings FOR SELECT USING (public.is_admin()); CREATE POLICY "Super admins can update settings" ON public.system_settings FOR UPDATE USING (public.is_super_admin());

C.3 Common Mistakes to Avoid

Learning from others' mistakes prevents you from wasting time on problems that are entirely avoidable.

Mistake 1: Skipping Verification
Every prompt includes verification steps. Skipping them creates invisible problems that compound later. If a verification step fails, fix it before proceeding.
Mistake 2: Modifying Quality Standards
The QUALITY STANDARDS section in each prompt exists to prevent vibe coding. Weakening or removing these requirements produces code that looks complete but fails in production.
Mistake 3: Running Prompts Out of Order
Prompts are designed to build on each other. Running Milestone 6 before Milestone 5 will fail because authentication doesn't exist yet. Always work sequentially.
Mistake 4: Incomplete Placeholders
If you see [PRODUCT NAME] in your output, you forgot to replace a placeholder. Review output for any remaining brackets before accepting code.
Mistake 5: Ignoring CONTEXT Section
The CONTEXT section tells Claude what already exists. If you skip previous milestones, update CONTEXT to reflect reality — otherwise Claude will reference files that don't exist.

C.4 When to Restart or Retry

Knowing when to iterate vs. restart saves time — small fixes are quick, but fundamental misunderstandings need a fresh start.

Sometimes Claude produces output that doesn't match requirements. When this happens:

  1. Minor issues: Ask Claude to fix the specific problem ("The UserCard component is missing the status badge")
  2. Structure issues: Clarify the requirement and ask for a revised version
  3. Major misunderstanding: Start a fresh conversation with a clearer prompt

If you find yourself fixing the same type of issue repeatedly, add it to your CLAUDE.md file as a project convention so future prompts account for it.
