PART I: FOUNDATION

Introduction: Why Structured Prompts Matter

Long, dense prompts fail for three predictable reasons. First, when too many requirements compete for attention, the AI loses focus on what matters most. Second, important details get buried in walls of text and get skipped. Third, without clear structure, the AI fills gaps with assumptions that may not match what you actually need.

This guide restructures the Build phase into clear, focused prompts that follow a consistent format. Each prompt is organized into labeled sections that are easy to scan. Each milestone includes explicit checkpoints for code quality, security, and functionality.

The Prompt Structure Philosophy

Every prompt in this guide follows the same six-section pattern, making them predictable and easy to work with.

ROLE establishes who the AI should act as. This grounds the AI in the right mindset before diving into specifics. A "Senior Full-Stack Developer" approaches problems differently than a "Junior Developer learning the ropes."

CONTEXT describes what exists right now. What files are in place. What has been completed in previous milestones. This prevents the AI from making incorrect assumptions about starting conditions, which is one of the most common sources of errors.

OBJECTIVE states the specific goal for this prompt. One clear objective per prompt. If you have multiple objectives, split them into multiple prompts. This focus is essential for quality output.

REQUIREMENTS provides detailed specifications organized by category. Functional requirements, quality requirements, and constraints are all separated so nothing gets lost. Each requirement is a separate line item that can be checked off.

QUALITY STANDARDS defines what "good" looks like. This is where the anti-vibe-coding safeguards live. Without explicit quality criteria, the AI optimizes for "looks complete" rather than "is maintainable."

DELIVERABLES & VERIFICATION specifies exactly what files should be produced and how to confirm the work is complete. This creates accountability and makes it easy to know when you're done.

Build Phase Overview

The Eleven Milestones

The Build phase is divided into eleven milestones, each building on the previous. Complete and verify each milestone before moving to the next. Rushing ahead creates a shaky foundation that causes problems later.

Major Checkpoints

In addition to per-milestone quality gates, there are three major checkpoints where you pause for deeper review.

Checkpoint A: After Milestone 3 (Database)

Before building features, verify the data foundation is solid. Review schema design. Confirm all RLS policies are in place. Test that policies actually work by attempting unauthorized access. This includes the admin tables if you're building the admin console.

Checkpoint B: After Milestone 7 (Admin Console)

The admin console provides your operational visibility. Verify you can find and view any user, see subscription statuses, and access error logs. Test admin role restrictions to ensure non-admins cannot access admin routes. This is your last checkpoint before building additional user-facing features.

Checkpoint C: After Milestone 10 (Polish)

Before final testing, ensure the codebase is clean. Run the full refactoring audit. Address all accumulated technical debt. Verify error handling is comprehensive. Confirm all states are handled in the UI.

PART III: ADMIN CONSOLE (MILESTONE 7)

Why the Admin Console Matters

The admin console is your control room. Without it, you're flying blind. When a customer reports an issue, you can't investigate their account. When you want to understand your business metrics, you have to write ad-hoc database queries. When something breaks in production, you're scrambling to find logs.

Building the admin console as Milestone 7 (after core feature, before additional features) is intentional. By this point, you have real data structures to manage and real functionality to monitor. Building it now means you have operational visibility while you're still actively developing and debugging.

Phase 1 Admin Features (This Milestone): These are the essential features you need from day one. User management (list, search, view), subscription viewing, and error log integration. Everything else can wait until after launch.

Admin Database Schema

Before building the admin console UI, you need to add admin-specific tables to your database. These should be included in your Milestone 3 database work, but if you're adding admin functionality to an existing project, create a new migration.

Security Check: Admin Console

The admin console has elevated privileges. Verify thoroughly:

  • Access Control: Non-admin users cannot access any /admin/* route
  • Role Checks: super_admin-only features hidden from regular admin
  • Audit Logging: All admin actions create audit log entries
  • No Data Leaks: Admin pages don't expose data in URL params or error messages
  • API Protection: Admin API routes verify admin role server-side
  • Action Confirmation: Destructive actions require confirmation

Quality Gate: Milestone 7

  • Admin dashboard loads with stats
  • User list with search and filters works
  • User detail shows all sections
  • Admin notes can be added and viewed
  • User actions (password reset, disable) work and log to audit
  • Subscription list shows correct MRR
  • Error log shows recent errors
  • Non-admin user cannot access /admin routes
  • All admin actions create audit log entries
  • No TypeScript errors

PART IV: REMAINING MILESTONES (8-11)

Milestone 8: Supporting Features

Apply the same four-prompt pattern from Milestone 6 (Data Layer, Server Actions, UI Components, Page Assembly) for each additional user-facing feature. Keep features small and focused. Complete and verify each feature before starting the next.

Milestone 9: Payments

Split into focused prompts covering Stripe configuration and webhook setup, the checkout flow implementation, billing management UI, and subscription status handling. Security is especially critical here since you're handling payment data.

Milestone 10: Polish

Split into prompts for error boundary implementation, loading state audit and improvement, empty state audit, edge case handling, and accessibility audit. This milestone ensures the application feels complete and professional.

Milestone 11: Testing

Split into prompts for test infrastructure setup, critical path E2E tests, unit tests for business logic, and integration tests for API routes. Focus on testing the paths that matter most: authentication, the money action, and payment flows.

APPENDIX A: POST-MVP ADMIN ROADMAP

These features are important but not launch-blocking. Build them after you have real users and understand your actual operational needs. They're documented here so you don't forget about them and have a starting point when you're ready.

Phase 2: Operational Features

Build these when you're handling regular support requests and need more powerful tools.

User Impersonation High Priority

What: Ability to see the app exactly as a specific user sees it, without knowing their password.

Why: When users report issues, you need to reproduce what they're experiencing. Screenshots and descriptions are often incomplete.

Implementation notes: Create a temporary session that sets the viewed user's ID but retains admin audit logging. Show clear visual indicator that you're in impersonation mode. Log all impersonation sessions. Limit impersonation duration (auto-expire after 30 minutes).

Manual Billing Adjustments High Priority

What: Extend trials, apply discounts, issue refunds, change plans, cancel subscriptions manually.

Why: Automated systems can't handle every situation. Good customer service sometimes requires making exceptions.

Implementation notes: All actions go through Stripe API, not direct database modification. Require reason field for audit log. Implement approval workflow for large refunds (require super_admin).

Feature Flags Medium Priority

What: Enable/disable features for all users or specific segments without deploying code.

Why: Allows gradual rollouts, beta testing with select users, and quick disable of broken features.

Implementation notes: Store flags in system_settings or dedicated table. Create useFeatureFlag hook for frontend. Cache flags to avoid per-request database hits. Support percentage rollouts and user segment targeting.

Audit Log Viewer Medium Priority

What: Searchable, filterable view of all admin actions.

Why: Accountability, security investigation, and compliance requirements.

Implementation notes: Already logging to admin_audit_logs from Phase 1. Build UI to search by admin, action type, target, date range. Add export to CSV functionality.

Bulk User Actions Low Priority

What: Select multiple users and perform actions (send email, apply tag, export data).

Why: Efficiency when dealing with groups of users (e.g., all trial users, all users on legacy plan).

Implementation notes: Implement carefully to avoid accidentally affecting wrong users. Require confirmation showing count. Process in background job for large batches.

Phase 3: Growth Features

Build these when you're actively optimizing for growth and need deeper insights.

Analytics Dashboard High Priority

What: User acquisition trends, engagement metrics (DAU/WAU/MAU), feature usage, conversion funnels.

Why: Understanding user behavior is essential for growth decisions.

Implementation notes: Can integrate with analytics service (Mixpanel, PostHog, Amplitude) or build from event tracking data. Focus on actionable metrics, not vanity metrics. Include cohort analysis for retention.

Revenue Analytics High Priority

What: MRR trends, churn analysis, LTV calculation, expansion revenue tracking.

Why: Financial health visibility is essential for a sustainable business.

Implementation notes: Pull from Stripe data. Show new MRR, churned MRR, expansion MRR, net MRR change. Calculate and display churn rate and LTV. Alert on unusual changes.

SEO Tools Medium Priority

What: Manage meta tags, Open Graph images, robots.txt, sitemap settings.

Why: SEO is important for organic growth, and marketers shouldn't need developers to update descriptions.

Implementation notes: Store settings in system_settings. Generate meta tags dynamically from settings. Include preview of how pages will appear in search results.

GDPR Compliance Tools Medium Priority

What: Data export (all user data in portable format), data deletion (complete erasure), consent management.

Why: Legal requirement in EU and increasingly expected by privacy-conscious users everywhere.

Implementation notes: Data export: gather from all tables, format as JSON/CSV, include Stripe data. Data deletion: soft-delete then hard-delete after verification period, anonymize records that must be retained. Log all GDPR requests for compliance records.

Advanced Monitoring Low Priority

What: Performance metrics, slow query identification, API response time tracking, uptime monitoring.

Why: Proactive performance management prevents user-facing issues.

Implementation notes: Integrate with APM service (Vercel Analytics, Datadog, New Relic) or build from request logging. Set up alerts for performance degradation. Track p50, p95, p99 response times.
