PART I: FOUNDATION

Philosophy, Quality Framework, and Tool Selection

Chapter 1: Introduction and Philosophy

1.1 The Vision

This handbook presents a methodology for building production-quality SaaS products using AI-assisted development. The goal is not just working code, but code that is secure, maintainable, testable, and ready for scale.

Version 3.0 introduces MOAI-ADK integration, which transforms the Build Phase from a series of prompts into a disciplined, test-driven development process where every feature begins with a specification and ends with verified, documented code.

The MOAI Principle

Specification Before Implementation. Every feature, no matter how small, starts with a SPEC that defines requirements, test cases, and acceptance criteria. Implementation follows the TDD cycle: write failing tests (RED), implement to pass (GREEN), improve code quality (REFACTOR).

1.2 Core Principles

Documentation Before Code

The most expensive bugs are architectural bugs. They compound over time and eventually require rewrites. The solution is to invest in documentation before writing code. This handbook enforces a documentation-first workflow where design decisions are made explicit before implementation begins.

Quality Is Non-Negotiable

Every piece of code must meet explicit quality standards. Functions must be appropriately sized. Error handling must be comprehensive. Security must be defense-in-depth. Performance must be considered from the start. These are not aspirational goals. They are requirements.

Verification at Every Step

Trust but verify. AI-generated artifacts can be impressive, but they can also be subtly wrong. Every artifact produced by the handbook workflow must be verified against explicit criteria before it feeds into subsequent stages.

Right Tool for the Task

Claude Chat and Claude Code CLI have different strengths. Using the right tool for each task dramatically improves outcomes. This handbook specifies which tool to use at each stage and why.

Chapter 2: The Code Quality Crisis

2.1 Understanding Vibe Coding

"Vibe coding" is a phenomenon where AI-generated code appears to work but fails to meet professional quality standards. The code passes visual inspection. It runs without errors in the happy path. But underneath, it is a maintenance nightmare waiting to happen.

The term captures the essence of the problem: the developer "goes with the vibe" rather than verifying the substance. The AI produced something that looks right, so it must be right. This assumption is dangerous.

2.2 The Six Failure Patterns

These patterns are predictable. Understanding them is the first step to preventing them.

Pattern 1: Monolithic Function Syndrome

The AI generates a single function that handles an entire feature: fetching data, transforming it, validating it, updating state, handling errors, and rendering output. This function might be 150 lines long. It technically works. But it cannot be tested in isolation, is impossible to understand at a glance, and any change risks breaking unrelated behavior.

Pattern 2: Copy-Paste Proliferation

When the AI needs similar functionality in multiple places, it often duplicates code with minor modifications rather than extracting shared logic. You end up with five slightly different implementations of the same pattern.

Pattern 3: Implicit Coupling

The AI creates code where components know too much about each other's internals. A UI component directly accesses database logic. A utility function assumes specific application state. These hidden dependencies make the code fragile.

Pattern 4: Security Afterthought

Input validation, authentication checks, and authorization logic get added inline wherever they seem needed. There is no systematic enforcement. Some paths are protected. Others are not.

Pattern 5: Performance Blindness

The AI generates code that works correctly but performs unnecessary operations. Data is re-fetched when it is already available. Values are re-computed on every render.

Pattern 6: Error Handling Inconsistency

Some functions have try-catch blocks. Others do not. Some errors are logged. Others are silently swallowed. There is no coherent strategy.

2.3 The Solution: Explicit Quality Standards

The solution is not to use AI less. It is to use AI more precisely. AI is incredibly responsive to guidance. When you provide explicit quality criteria, the AI will meet them. When you do not, the AI will optimize for what it can infer: something that looks complete.

Chapter 3: The Quality Framework - Five Pillars

The quality framework provides concrete standards for evaluating code. It is organized into five pillars: Structure, Simplicity, Safety, Speed, and Stability.

3.1 Structure

Structure is about organizing code so that each piece has a clear purpose and location.

Key Principles

  • Single Responsibility: Every function, component, and module should do one thing.
  • Appropriate Abstraction: Code at the same level should operate at the same abstraction level.
  • Explicit Dependencies: No reaching into global state. Dependencies come through parameters, props, or imports.
  • Cohesive Modules: Group related functionality. Separate unrelated functionality.

3.2 Simplicity

Simplicity is about minimizing cognitive load.

Key Principles

  • Function Length: Functions should rarely exceed 20-30 lines.
  • Nesting Depth: Maximum 3 levels. Use early returns to reduce nesting.
  • Naming Clarity: Names should reveal intent. "userSubscriptionStatus" beats "data".
  • No Magic Values: Named constants for all numbers and strings in logic.

3.3 Safety

Safety encompasses security and correctness. Security is not an afterthought — it must be built into every layer from the start.

Key Principles

  • Input Validation at Boundaries: All external data validated once, at entry. Use Zod schemas for type-safe validation.
  • Defense in Depth: Multiple layers of security checks. API routes validate AND RLS enforces. Never rely on a single layer.
  • Fail Securely: Errors should not expose sensitive information. Log details server-side, show generic messages client-side.
  • Explicit Error Handling: Every operation that can fail should have explicit handling. No silent failures.

Security Requirements (OWASP-Aligned)

  • Authentication: Use Supabase Auth. Never roll custom auth. Enforce password policies.
  • Authorization: RLS on every table. Check permissions in API routes AND database. Test with different user roles.
  • Injection Prevention: Use parameterized queries (Supabase client does this). Never concatenate user input into queries.
  • XSS Prevention: React escapes by default. Never use dangerouslySetInnerHTML with user content. Sanitize if you must render HTML.
  • CSRF Protection: Use Server Actions (built-in protection) or validate Origin headers on API routes.
  • Secrets Management: Environment variables only. Never commit secrets. Never expose server keys to client.
  • Security Headers: Configure HSTS, X-Frame-Options, CSP in next.config.js.
  • Dependency Security: Run npm audit before every release. No high/critical vulnerabilities in production.

Security Checklist for Every Feature

  • Does this feature accept user input? → Validate with Zod
  • Does this feature display user content? → Ensure proper escaping
  • Does this feature access data? → RLS policy in place and tested
  • Does this feature have admin-only actions? → Role check in code AND RLS
  • Does this feature handle sensitive data? → Never log, never expose in errors

3.4 Speed

Speed is about performance and efficiency.

Key Principles

  • Avoid Unnecessary Work: Do not compute, fetch, or render what is not needed.
  • Appropriate Data Structures: Choose structures that match access patterns.
  • Database Efficiency: No N+1 queries. Select only needed columns. Use indexes.
  • Measure Before Optimizing: Profile real performance. Optimize actual bottlenecks.

3.5 Stability

Stability is about reliability and maintainability.

Key Principles

  • Test Coverage: Critical paths have automated tests.
  • Consistent Patterns: Similar problems solved similarly throughout.
  • Documentation at Decision Points: Comments explain "why" for non-obvious choices.
  • Observable Behavior: Sufficient logging and metrics for production debugging.

3.6 Quality Gate Definitions

SPEC Quality Gate (Before Implementation)

  • At least one requirement defined
  • Each requirement has at least one test case
  • Requirements use EARS format
  • Test cases use GIVEN-WHEN-THEN format
  • Build Contract sections referenced
  • Acceptance criteria defined

Implementation Quality Gate (After Implementation)

  • All test cases pass
  • Code meets structure standards (functions <30 lines, files <200 lines)
  • Security checks present
  • No TypeScript errors
  • Linting passes
  • Coverage >= 80%

PART III: DESIGN EXCELLENCE

Chapter 8-10: UX Package and Validation

8.1 Design Philosophy

Good design is invisible. Users should accomplish their goals without thinking about the interface. Every screen should have a clear purpose, every element should earn its place, and every interaction should feel natural.

Core Principles

  • Clarity over Cleverness: Obvious is better than innovative
  • Progressive Disclosure: Show what's needed, hide complexity
  • Consistent Patterns: Same action, same behavior everywhere
  • Forgiving Design: Easy to recover from mistakes
  • Performance as Feature: Fast feels professional

9.1 UX Package Purpose

The UX Package defines the complete user experience: all screens, all flows, all states. It serves as the blueprint for UI design and development.

9.2 UX Package Prompt

Create a UX Package for [PRODUCT NAME]. **Design Brief**: [ATTACH OR REFERENCE] The UX Package should include: **SECTION 1: Information Architecture** - Site map showing all screens/routes - Navigation structure - User flow diagrams **SECTION 2: Screen Inventory** For each screen: - Screen name and route - Purpose (what user accomplishes) - Entry points (how user arrives) - Exit points (where user goes next) - Key components - Data displayed/collected - Actions available - Error states - Loading states - Empty states **SECTION 3: User Flows** For each core flow from Design Brief: - Step-by-step sequence - Decision points - Error recovery paths - Success confirmation **SECTION 4: Component Behaviors** - Form validation rules - Confirmation dialogs (when and what) - Notification patterns - Loading indicators **SECTION 5: Responsive Behavior** - Breakpoints - What changes at each breakpoint - Mobile-specific interactions

10.1 UX Critique

Before proceeding to UI, the UX Package should be critiqued for usability issues, missing states, and flow problems.

Review this UX Package as a UX expert. Identify: 1. **Usability Issues**: Friction points, confusing flows, cognitive overload 2. **Missing States**: Empty states, error states, loading states not defined 3. **Edge Cases**: Scenarios not covered 4. **Accessibility Gaps**: Issues for users with disabilities 5. **Mobile Considerations**: Touch targets, thumb zones, scrolling For each issue, suggest a specific improvement. Chapter 19: Multi-Environment Configuration

A proper multi-environment setup is essential for professional SaaS development. This chapter provides a complete guide to configuring three isolated environments: Development, Staging (Preview), and Production.

19.1 Environment Strategy Overview

The three-environment model provides isolation between development work, testing/review, and production users. Each environment connects to its own Supabase project and uses the appropriate Stripe mode.

Why Three Separate Projects?

Three Supabase projects provides complete data isolation. Preview testers don't pollute your development data. Production data is completely separate from test data. This isolation is worth the minor cost increase and prevents data contamination issues that are painful to debug.

19.2 Supabase Project Setup

Create three separate Supabase projects to ensure complete environment isolation.

Step 1: Create Development Project

  1. Go to supabase.com and sign in
  2. Click "New Project"
  3. Name: [project-name]-dev
  4. Database password: Generate a strong password and save it securely
  5. Region: Choose closest to your location (for faster development)
  6. Wait for project to provision (~2 minutes)

Step 2: Create Staging Project

  1. Click "New Project" again
  2. Name: [project-name]-staging
  3. Database password: Generate a different strong password
  4. Region: Same as your production target region (to match behavior)

Step 3: Create Production Project

  1. Click "New Project"
  2. Name: [project-name]-prod
  3. Database password: Generate a different strong password
  4. Region: Choose based on your target users (e.g., us-east-1 for US users)

Step 4: Configure Auth Settings

Repeat for each project. Go to Authentication → URL Configuration:

Project Site URL Redirect URLs
Dev http://localhost:3000 http://localhost:3000/**
Staging https://[project]-*-[username].vercel.app https://*-[username].vercel.app/**
Prod https://[your-domain].com https://[your-domain].com/**

For each project, go to Authentication → Providers and enable your chosen auth methods (Email, OAuth providers, etc.).

Step 5: Enable Row Level Security

Critical Security Requirement

RLS must be enabled on ALL tables in ALL environments. Never disable RLS in production. This is your primary data access control layer.

-- Run this for each table you create ALTER TABLE your_table_name ENABLE ROW LEVEL SECURITY; -- Example: Enable RLS on user_profiles ALTER TABLE user_profiles ENABLE ROW LEVEL SECURITY;

Step 6: Record Your Credentials

From each project's Settings → API, record these values:

Project Project URL Anon Key Service Role Key DB Password

Staging https://[ref].supabase.co eyJ... eyJ... (saved securely)
Prod https://[ref].supabase.co eyJ... eyJ... (saved securely)

Never Commit Credentials

These values go in Vercel environment variables only. Never commit them to your repository. Add .env.local to your .gitignore file.

19.3 Local Development Setup

Your local development environment connects to the cloud Development Supabase project. This approach is simpler than running Supabase locally via Docker and requires no additional infrastructure.

Prerequisites

  • Node.js 20+ installed
  • npm or pnpm package manager
  • Supabase CLI: npm install -g supabase
  • Vercel CLI: npm install -g vercel
  • Git configured with your credentials

Step 1: Clone and Install

git clone [your-repo-url] cd [project-name] npm install

Step 2: Link to Vercel Project

vercel link # Follow prompts to connect to your Vercel project # Select your team/account and project when prompted

Step 3: Pull Environment Variables

vercel env pull .env.local # This creates .env.local with Development environment variables

Step 4: Verify Connection

npm run dev # Open http://localhost:3000 # Verify auth and database connections work

Step 5: Link Supabase CLI (for migrations)

supabase login supabase link --project-ref [your-dev-project-ref] # Project ref is in your Supabase project URL: # supabase.com/dashboard/project/[ref]

Shared Development Database

Your local development connects to the cloud Development Supabase project. Changes to the database (via the app or migrations) affect this shared environment. If working with a team, coordinate database changes to avoid conflicts.

19.7 Database Migration Workflow

Migrations are version-controlled SQL files that evolve your database schema. Create migrations in development, test in staging, then apply to production.

Setting Up Supabase CLI for Migrations

# Initialize Supabase in your project (if not done) supabase init # Link to your Development project supabase link --project-ref [your-dev-project-ref] # Project ref is found in: supabase.com/dashboard/project/[ref]

This creates a supabase/ directory:

supabase/ +-- config.toml +-- migrations/ | +-- (migration files go here) +-- seed.sql (optional)

Creating a New Migration

# Create a new migration file supabase migration new add_user_profiles_table # This creates: supabase/migrations/[timestamp]_add_user_profiles_table.sql

Edit the migration file with your SQL:

-- supabase/migrations/20240115120000_add_user_profiles_table.sql CREATE TABLE user_profiles ( id UUID PRIMARY KEY DEFAULT gen_random_uuid(), user_id UUID REFERENCES auth.users(id) ON DELETE CASCADE, full_name TEXT, avatar_url TEXT, created_at TIMESTAMPTZ DEFAULT NOW(), updated_at TIMESTAMPTZ DEFAULT NOW() ); -- Enable RLS (REQUIRED) ALTER TABLE user_profiles ENABLE ROW LEVEL SECURITY; -- RLS Policies CREATE POLICY "Users can view own profile" ON user_profiles FOR SELECT USING (auth.uid() = user_id); CREATE POLICY "Users can update own profile" ON user_profiles FOR UPDATE USING (auth.uid() = user_id); CREATE POLICY "Users can insert own profile" ON user_profiles FOR INSERT WITH CHECK (auth.uid() = user_id);

Applying Migrations

To Development (remote)

supabase db push # Applies all pending migrations to your linked (Dev) project

To Staging

Option 1: Link temporarily via CLI

supabase link --project-ref [your-staging-project-ref] supabase db push supabase link --project-ref [your-dev-project-ref] # Re-link to dev

Option 2: Use Supabase Dashboard

  1. Go to Staging project → SQL Editor
  2. Copy migration SQL and run manually
  3. Verify tables created correctly

To Production

Production Migration Safety

Production migrations require extra care. Always create a backup first. Review the migration SQL carefully before applying.

# Create a backup first (Supabase Pro feature) # Go to Project Settings -> Database -> Backups -> Create backup # Option 1: Via CLI (link temporarily) supabase link --project-ref [your-prod-project-ref] supabase db push supabase link --project-ref [your-dev-project-ref] # Re-link to dev # Option 2: Via Dashboard (recommended for production) # Copy migration SQL, review carefully, run in SQL Editor

Migration Best Practices

Migration Checklist

  • Each migration should be atomic (one logical change)
  • Consider rollback strategy for each migration
  • Always enable RLS on new tables
  • Test migration on Dev before Staging
  • Test migration on Staging before Production
  • Create production backup before applying
  • Commit migration files to version control

Handling Schema Drift

If someone makes direct changes via Supabase Dashboard:

# Pull remote schema changes to local migration supabase db pull # This creates a migration file with the differences # Review and commit to version control

Prefer Migrations Over Dashboard Edits

Direct Dashboard edits create schema drift that's hard to track. Prefer using migrations for all schema changes so they're version controlled and reproducible across environments.

19.8 Troubleshooting Common Issues

Issue: "Invalid API key" errors

  • Cause: Wrong Supabase environment variables
  • Fix: Verify you're using the correct project's keys for each environment
  • Check: Ensure NEXT_PUBLIC_SUPABASE_URL matches the expected project

Issue: Auth redirects to wrong URL

  • Cause: Site URL not configured in Supabase Auth settings
  • Fix: Add the deployment URL to Supabase → Authentication → URL Configuration → Redirect URLs
  • For Preview: Add wildcard pattern https://*-[your-vercel-username].vercel.app/**

Issue: RLS blocking all queries

  • Cause: Missing or incorrect RLS policies
  • Fix: Check policies in Supabase → Authentication → Policies
  • Debug: Temporarily use service role key (server-side only) to verify data exists

Issue: Stripe webhooks failing

  • Cause: Wrong webhook secret or URL
  • Fix: Verify STRIPE_WEBHOOK_SECRET matches the endpoint's signing secret
  • Debug: Check Stripe Dashboard → Webhooks → Recent events for error details

Issue: Environment variables not updating

  • Cause: Vercel caches environment variables per deployment
  • Fix: Trigger a new deployment after changing env vars
  • Quick fix: Vercel Dashboard → Deployments → Redeploy

Issue: Preview deployment can't connect to Staging Supabase

  • Cause: Preview environment variables pointing to wrong project
  • Fix: Ensure Preview-scoped variables point to Staging Supabase project URL and keys

Issue: Local development connecting to wrong database

  • Cause: Stale .env.local file
  • Fix: Re-run vercel env pull .env.local to get latest Development variables

Chapter 27: Technical Debt Scoring Framework NEW

Technical debt is inevitable during rapid development. The difference between successful projects and troubled ones is not the absence of debt — it's the awareness and management of that debt. This framework provides objective measurement so you can make informed decisions about when to incur debt, when to pay it down, and when to stop and remediate.

27.1 Why Measure Technical Debt

Without measurement, debt accumulates invisibly until it blocks progress. Common symptoms of unmanaged debt:

  • Simple changes require touching many files
  • New developers take weeks to understand the codebase
  • Bugs keep appearing in the same areas
  • Fear of refactoring because "it might break something"
  • Test suite takes too long or provides false confidence

The scoring framework makes debt visible and actionable. Run it at every checkpoint to catch problems early.

27.2 The Six Debt Categories

Category Weight What It Measures Automated?
Code Complexity 25% Function length, nesting depth, cyclomatic complexity Yes (ESLint)
Error Handling 20% No empty catches, consistent patterns, explicit handling Yes (ESLint)
Type Safety 20% Zero any types, strict mode, explicit returns Yes (TypeScript + ESLint)
Test Coverage 20% Line coverage percentage for business logic Yes (Jest/Vitest)
Documentation Sync 10% CLAUDE.md current, SPECs match implementation No (Manual review)
Dependency Health 5% npm audit clean, dependencies up to date Yes (npm audit)

27.3 Scoring Each Category (1-10 Scale)

Code Complexity Score

# Run ESLint with complexity rules npm run lint # Scoring: # 10: Zero complexity violations # 8-9: Only warnings, no errors # 6-7: 1-5 complexity errors # 4-5: 6-15 complexity errors # 1-3: 16+ complexity errors or ignored rules

What triggers complexity violations:

  • Functions exceeding 30 lines
  • Files exceeding 200 lines
  • Nesting depth greater than 3
  • Cyclomatic complexity greater than 10
  • More than 4 function parameters

Error Handling Score

# Check for empty catch blocks grep -r "catch.*{.*}" src/ --include="*.ts" --include="*.tsx" | grep -v "// handled" # Scoring: # 10: All errors explicitly handled, consistent patterns # 8-9: Minor inconsistencies # 6-7: Some empty catches with comments # 4-5: Multiple empty catches, inconsistent patterns # 1-3: Errors swallowed or ignored systematically

Type Safety Score

# Check for any types grep -r ": any" src/ --include="*.ts" --include="*.tsx" | wc -l # Check TypeScript strict mode grep "strict" tsconfig.json # Scoring: # 10: Zero any types, strict mode enabled # 8-9: 1-3 any types with justification # 6-7: 4-10 any types # 4-5: 11-25 any types or strict mode disabled # 1-3: 26+ any types or no TypeScript

Test Coverage Score

# Run tests with coverage npm test -- --coverage # Scoring: # 10: 90%+ coverage # 9: 80-89% coverage # 8: 70-79% coverage # 7: 60-69% coverage # 6: 50-59% coverage # 1-5: Below 50% coverage

Documentation Sync Score

Manual checklist (run at checkpoints):

  • CLAUDE.md reflects current project state
  • All completed SPECs marked as "Done"
  • Build Contract matches implementation
  • No orphaned TODO comments older than 1 week
  • README has accurate setup instructions

Scoring: 2 points per item checked (max 10)

Dependency Health Score

# Check for vulnerabilities npm audit # Check for outdated packages npm outdated # Scoring: # 10: Zero vulnerabilities, all deps current # 8-9: Zero high/critical, minor outdated deps # 6-7: 1-2 high vulnerabilities # 4-5: 3-5 high vulnerabilities or 1 critical # 1-3: Multiple critical vulnerabilities

27.4 Calculating the Overall Score

Overall Score = (Complexity × 0.25) + (ErrorHandling × 0.20) + (TypeSafety × 0.20) + (TestCoverage × 0.20) + (DocSync × 0.10) + (Dependencies × 0.05) Example: Complexity: 8 × 0.25 = 2.00 ErrorHandling: 7 × 0.20 = 1.40 TypeSafety: 9 × 0.20 = 1.80 TestCoverage: 8 × 0.20 = 1.60 DocSync: 6 × 0.10 = 0.60 Dependencies: 10 × 0.05 = 0.50 ───────────────────────────── Overall Score: 7.90

27.5 Score Thresholds and Actions

Score Rating Action
≥ 8.0 Excellent Proceed confidently. Debt is well-managed.
7.0 - 7.9 Good Minor debt exists. Document in TECH-DEBT.md and proceed.
6.0 - 6.9 Acceptable Create remediation plan. Proceed with awareness. Address before next checkpoint.
5.0 - 5.9 Concerning Address high-priority items before proceeding. Allocate time in next milestone.
< 5.0 Critical STOP. Do not proceed until score reaches 6.0+. Remediation is now the priority.
Checkpoint Gate: At Checkpoint A and B, a score below 6.0 is a hard stop. Do not proceed to the next milestone until debt is remediated to at least 6.0.

27.6 Tracking Debt Over Time

Create a TECH-DEBT.md file in your project root to track debt items. Update it at every checkpoint.

# TECH-DEBT.md structure project-root/ ├── TECH-DEBT.md # Debt registry ├── CLAUDE.md # AI context ├── docs/ │ ├── build-contract.md │ └── specs/ └── src/

Each debt item should include:

  • Location: File and line number
  • Category: Which of the 6 categories
  • Severity: Critical, High, Medium, Low
  • Reason for deferral: Why not fix now
  • Remediation estimate: Hours or T-shirt size
  • Revisit date: When to address

PART VI: LAUNCH

Production Readiness and Go-Live

Chapter 30: QA and Launch Checklist

30.1 Why the Launch Phase Matters

The Launch phase ensures your application is production-ready. Skipping these checks leads to embarrassing bugs in front of real users, security vulnerabilities, and poor performance that drives users away. This phase connects all previous work — your design, architecture, and implementation — into a verified, deployable product.

30.2 How Launch Supports the Process

Launch is not just "pushing to production." It's the final quality gate that validates:

  • Design intentions are realized — UX flows work as specified
  • Architecture is sound — Performance meets requirements
  • Implementation is complete — All features work, all tests pass
  • Security is enforced — RLS policies, auth, and data protection verified

30.3 Pre-Launch Workflow

Pre-Launch Checklist

  • All tests passing, no TypeScript errors, no linting errors
  • Environment variables secured, RLS policies tested
  • Lighthouse score >= 90, Core Web Vitals passing
  • All user flows tested, mobile responsive verified
  • Error monitoring configured, analytics configured
  • Database backups enabled, domain configured

2. Security Verification (OWASP-Based)

Security must be verified systematically. Use this checklist based on OWASP Top 10 vulnerabilities:

Critical: Do not skip security verification. A single vulnerability can compromise all user data and destroy trust.
2.1 Authentication & Session Management
# Verify password policies (Supabase Auth settings) # Dashboard → Authentication → Policies # - Minimum 8 characters # - Require mix of letters/numbers recommended # Test session expiry # 1. Log in, note the session # 2. Wait for token expiry (or manually expire in Supabase) # 3. Verify user is prompted to re-authenticate # Verify secure cookie settings (check browser DevTools) # - HttpOnly: true # - Secure: true (HTTPS only) # - SameSite: Lax or Strict
2.2 Authorization & Access Control
# Test RLS policies by attempting unauthorized access # In Supabase SQL Editor, run as different roles: SET LOCAL ROLE anon; SELECT * FROM profiles; -- Should return empty or error SET LOCAL ROLE authenticated; SELECT * FROM profiles; -- Should only return own profile # Test horizontal privilege escalation # 1. Log in as User A # 2. Try to access User B's data via direct URL/API # 3. Should be denied by RLS # Test vertical privilege escalation # 1. Log in as regular user # 2. Try to access /admin routes # 3. Should be redirected or denied
2.3 Input Validation & Injection Prevention
# Test for SQL injection (should be prevented by Supabase client) # Try entering in form fields: # ' OR '1'='1 # '; DROP TABLE users; -- # Test for XSS (Cross-Site Scripting) # Try entering in any text field that displays user content: # <script>alert('XSS')</script> # <img src=x onerror=alert('XSS')> # Verify scripts do NOT execute (content should be escaped) # Verify Zod validation on all API routes grep -r "z\." src/app/api/ --include="*.ts" # All API routes should have input validation

The File Control System enables MOAI workflow by establishing clear locations for every artifact. When Claude Code or any AI assistant needs to reference your design decisions, architecture, or requirements, it knows exactly where to look. Without this structure:
