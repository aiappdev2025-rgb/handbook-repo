24.1 EARS Requirements Format

EARS (Easy Approach to Requirements Syntax) provides five patterns for writing unambiguous requirements. Using these patterns ensures your requirements are testable and clear.

TypePatternExample
UbiquitousThe [system] shall [action]The upload zone shall accept JPEG, PNG, and HEIC formats.
State-DrivenWhile [state], the [system] shall [action]While uploading, the system shall display progress.
Event-DrivenWhen [event], the [system] shall [action]When user clicks generate, the system shall call the AI API.
OptionalWhere [condition], the [system] shall [action]Where user is Pro tier, the system shall enable all styles.
UnwantedThe [system] shall not [action]The system shall not store raw API keys.

24.2 Test Case Format

Test cases use the GIVEN-WHEN-THEN format, which clearly separates preconditions, actions, and expected outcomes. This format maps directly to test code structure.

### TC-PHOTO-001: Valid image upload **GIVEN** a user is on the create listing page AND the user has selected a valid JPEG image **WHEN** the user drops the image on the upload zone **THEN** the system displays an upload progress indicator AND the image appears in the preview grid after upload completes

What You Need to Do

  1. Write SPECs before coding — For each feature, create a SPEC document in docs/specs/ using the template in Appendix B
  2. Use EARS format for requirements — Every requirement must follow one of the five EARS patterns above
  3. Create test cases for each requirement — At minimum, one test case per requirement; complex requirements may need multiple
  4. Reference Build Contract sections — Each SPEC must cite the relevant Build Contract sections it implements

Manual Steps:

Chapter 25: TDD Workflow

In this chapter, you'll learn the TDD (Test-Driven Development) workflow—the RED → GREEN → REFACTOR cycle that ensures every feature is properly tested. This workflow is the core of MOAI implementation. By the end of this chapter, you'll know exactly how to transform SPECs into working code.

📖 Read for Understanding — Understand the RED → GREEN → REFACTOR cycle. You'll follow this exact workflow for every feature during milestone execution.

25.1 The TDD Cycle

TDD follows a strict three-phase cycle. Each phase has a specific purpose and discipline.

TDD CYCLE: RED --> GREEN --> REFACTOR --> DONE RED: Write failing tests from SPEC test cases GREEN: Write minimum code to pass tests REFACTOR: Improve code quality, tests still pass DONE: All tests pass, quality gate passed

What You Need to Do

For each feature, follow the TDD cycle strictly:

RED Phase (Write Failing Tests)
  1. Take test cases from your SPEC document
  2. Create test file in src/__tests__/ following naming convention: [feature].test.ts
  3. Write tests that describe expected behavior
  4. Run tests — they should FAIL (this confirms you're testing the right thing)

Manual Steps:

# Create test file touch src/__tests__/auth.test.ts # Write tests based on SPEC test cases # Run tests to confirm failure npm test

With Claude Code:

claude "Write failing tests for SPEC-AUTH-001. Create src/__tests__/auth.test.ts Use the test cases defined in the SPEC. Do not write implementation yet."
GREEN Phase (Make Tests Pass)
  1. Write the minimum code needed to pass each test
  2. Do not over-engineer — just make the test pass
  3. Run tests after each change to verify progress

With Claude Code:

claude "Implement the minimum code to make auth.test.ts pass. Follow the requirements in SPEC-AUTH-001."
REFACTOR Phase (Improve Code Quality)
  1. Clean up code while keeping tests green
  2. Extract reusable functions, improve naming, add types
  3. Run tests after each refactor to ensure nothing breaks

Quality Gate Check:

# All tests must pass npm test # No TypeScript errors npm run build # No linting errors npm run lint
Detailed TDD prompts and milestone guides are in the Build Phase Guide v3.

Expected Outcome

What you should understand: The RED → GREEN → REFACTOR cycle and how each phase contributes to code quality.

What you should be able to do: Execute the TDD workflow for any SPEC—write failing tests, implement to pass, then refactor while keeping tests green.

Chapter 26: Technical Debt Scoring Framework NEW

In this chapter, you'll learn the Technical Debt Scoring Framework—a systematic way to measure and manage code quality degradation. Understanding technical debt helps you make informed decisions about when to incur debt and when to pay it down. By the end of this chapter, you'll have automated tools to track debt throughout your project.

📖 Read + Setup — Understand the scoring methodology, then copy the automation templates to your project. You'll run debt audits at each checkpoint during the build phase.

Technical debt is inevitable during rapid development. The difference between successful projects and troubled ones is not the absence of debt—it's the awareness and management of that debt. This framework provides objective measurement so you can make informed decisions about when to incur debt, when to pay it down, and when to stop and remediate.

26.1 Why Measure Technical Debt

Without measurement, debt accumulates invisibly until it blocks progress. Common symptoms of unmanaged debt:

  • Simple changes require touching many files
  • New developers take weeks to understand the codebase
  • Bugs keep appearing in the same areas
  • Fear of refactoring because "it might break something"
  • Test suite takes too long or provides false confidence

The scoring framework makes debt visible and actionable. Run it at every checkpoint to catch problems early.

26.2 The Six Debt Categories

Technical debt is measured across six categories, each with a specific weight reflecting its impact on long-term maintainability.

Category Weight What It Measures Automated?
Code Complexity 25% Function length, nesting depth, cyclomatic complexity Yes (ESLint)
Error Handling 20% No empty catches, consistent patterns, explicit handling Yes (ESLint)
Type Safety 20% Zero any types, strict mode, explicit returns Yes (TypeScript + ESLint)
Test Coverage 20% Line coverage percentage for business logic Yes (Jest/Vitest)
Documentation Sync 10% CLAUDE.md current, SPECs match implementation Partial (see 27.3.5)
Dependency Health 5% npm audit clean, dependencies up to date Yes (npm audit)

26.3 Scoring Each Category (1-10 Scale)

Each category is scored on a 1-10 scale using automated tools where possible. Consistent scoring criteria ensure objective measurement across checkpoints.

Code Complexity Score

# Run ESLint with complexity rules npm run lint # Scoring: # 10: Zero complexity violations # 8-9: Only warnings, no errors # 6-7: 1-5 complexity errors # 4-5: 6-15 complexity errors # 1-3: 16+ complexity errors or ignored rules

What triggers complexity violations:

  • Functions exceeding 30 lines
  • Files exceeding 200 lines
  • Nesting depth greater than 3
  • Cyclomatic complexity greater than 10
  • More than 4 function parameters

Error Handling Score

# Check for empty catch blocks grep -r "catch.*{.*}" src/ --include="*.ts" --include="*.tsx" | grep -v "// handled" # Scoring: # 10: All errors explicitly handled, consistent patterns # 8-9: Minor inconsistencies # 6-7: Some empty catches with comments # 4-5: Multiple empty catches, inconsistent patterns # 1-3: Errors swallowed or ignored systematically

Type Safety Score

# Check for any types grep -r ": any" src/ --include="*.ts" --include="*.tsx" | wc -l # Check TypeScript strict mode grep "strict" tsconfig.json # Scoring: # 10: Zero any types, strict mode enabled # 8-9: 1-3 any types with justification # 6-7: 4-10 any types # 4-5: 11-25 any types or strict mode disabled # 1-3: 26+ any types or no TypeScript

Test Coverage Score

# Run tests with coverage npm test -- --coverage # Scoring: # 10: 90%+ coverage # 9: 80-89% coverage # 8: 70-79% coverage # 7: 60-69% coverage # 6: 50-59% coverage # 1-5: Below 50% coverage

27.3.5 Documentation Sync Score

Documentation sync is partially automated via scripts/spec-check.sh:

Automated Checks (via spec-check.sh)

# Run the SPEC verification script ./scripts/spec-check.sh # Or in JSON format for CI ./scripts/spec-check.sh --json

The script checks:

  • SPEC Status: All SPECs have Status: Done
  • SPEC-Test Links: Each SPEC has a test file with // SPEC: SPEC-XXX-NNN comment
  • Test Case IDs: Test case IDs (TC-001, etc.) from SPEC appear in test file
  • Orphaned TODOs: No TODO comments older than 7 days (git blame)
  • CLAUDE.md exists: File present at project root

Manual Checks (still required)

  • CLAUDE.md content reflects current project state
  • Build Contract matches implementation
  • README has accurate setup instructions

Scoring: Automated script produces 0-10 score. Deduct 1 point per manual check that fails.

SPEC-Test Linking Convention: Test files must include a comment linking to their SPEC:
// SPEC: SPEC-AUTH-001 describe('User Authentication', () => { // TC-001: User can log in with valid credentials it('should authenticate user with valid email and password', () => { ... }); });

Dependency Health Score

# Check for vulnerabilities npm audit # Check for outdated packages npm outdated # Scoring: # 10: Zero vulnerabilities, all deps current # 8-9: Zero high/critical, minor outdated deps # 6-7: 1-2 high vulnerabilities # 4-5: 3-5 high vulnerabilities or 1 critical # 1-3: Multiple critical vulnerabilities

26.4 Calculating the Overall Score

The weighted formula combines all category scores into a single number that represents overall code health. This makes it easy to track trends and make go/no-go decisions at checkpoints.

Overall Score = (Complexity x 0.25) + (ErrorHandling x 0.20) + (TypeSafety x 0.20) + (TestCoverage x 0.20) + (DocSync x 0.10) + (Dependencies x 0.05) Example: Complexity: 8 x 0.25 = 2.00 ErrorHandling: 7 x 0.20 = 1.40 TypeSafety: 9 x 0.20 = 1.80 TestCoverage: 8 x 0.20 = 1.60 DocSync: 6 x 0.10 = 0.60 Dependencies: 10 x 0.05 = 0.50 ---------------------------- Overall Score: 7.90

26.5 Score Thresholds and Actions

Knowing your score is only useful if you know what action to take. These thresholds define clear decision criteria for each checkpoint.

Score Rating Action
>= 8.0 Excellent Proceed confidently. Debt is well-managed.
7.0 - 7.9 Good Minor debt exists. Document in TECH-DEBT.md and proceed.
6.0 - 6.9 Acceptable Create remediation plan. Proceed with awareness. Address before next checkpoint.
5.0 - 5.9 Concerning Address high-priority items before proceeding. Allocate time in next milestone.
< 5.0 Critical STOP. Do not proceed until score reaches 6.0+. Remediation is now the priority.
Checkpoint Gate: At Checkpoint A and B, a score below 6.0 is a hard stop. Do not proceed to the next milestone until debt is remediated to at least 6.0.

26.6 Generating and Updating TECH-DEBT.md

Manual debt tracking is error-prone and often forgotten. Automating the audit process ensures consistent measurement and creates a historical record you can reference to understand trends.

At each checkpoint, use Claude Code to run all debt checks and generate/update TECH-DEBT.md:

Claude Code At Checkpoints (run at Checkpoint A, B, and C)

Current checkpoint name and date 2. Overall score and category breakdown 3. Comparison to previous checkpoint (if exists) 4. Active debt items with severity (Critical/High/Medium/Low) 5. Resolved items since last checkpoint 6. Chapter 28: QA and Launch Checklist

In this chapter, you'll learn the QA and launch checklist that ensures your application is production-ready. This is the final quality gate before real users see your product. By the end of this chapter, you'll have a complete launch verification workflow.

28.1 Why the Launch Phase Matters

The Launch phase ensures your application is production-ready. Skipping these checks leads to embarrassing bugs in front of real users, security vulnerabilities, and poor performance that drives users away. This phase connects all previous work — your design, architecture, and implementation — into a verified, deployable product.

28.2 How Launch Supports the Process

Launch is not just "pushing to production." It's the final quality gate that validates:

  • Design intentions are realized — UX flows work as specified
  • Architecture is sound — Performance meets requirements
  • Implementation is complete — All features work, all tests pass
  • Security is enforced — RLS policies, auth, and data protection verified

28.3 Pre-Launch Workflow

The pre-launch workflow ensures nothing critical is missed before users see your product. Work through each category systematically—rushing this phase creates embarrassing bugs and security vulnerabilities.

Pre-Launch Checklist

  • All tests passing, no TypeScript errors, no linting errors
  • Environment variables secured, RLS policies tested
  • Lighthouse score >= 90, Core Web Vitals passing
  • All user flows tested, mobile responsive verified
  • Error monitoring configured, analytics configured
  • Database backups enabled, domain configured

2. Security Verification (OWASP-Based)

Security must be verified systematically. Use this checklist based on OWASP Top 10 vulnerabilities:

Critical: Do not skip security verification. A single vulnerability can compromise all user data and destroy trust.
2.1 Authentication & Session Management
# Verify password policies (Supabase Auth settings) # Dashboard -> Authentication -> Policies # - Minimum 8 characters # - Require mix of letters/numbers recommended # Test session expiry # 1. Log in, note the session # 2. Wait for token expiry (or manually expire in Supabase) # 3. Verify user is prompted to re-authenticate # Verify secure cookie settings (check browser DevTools) # - HttpOnly: true # - Secure: true (HTTPS only) # - SameSite: Lax or Strict

# Test RLS policies by attempting unauthorized access # In Supabase SQL Editor, run as different roles: SET LOCAL ROLE anon; SELECT * FROM profiles; -- Should return empty or error SET LOCAL ROLE authenticated; SELECT * FROM profiles; -- Should only return own profile # Test horizontal privilege escalation # 1. Log in as User A # 2. Try to access User B's data via direct URL/API # 3. Should be denied by RLS # Test vertical privilege escalation # 1. Log in as regular user # 2. Try to access /admin routes # 3. Should be redirected or denied

2.5 Security Headers

Add to next.config.js:

Verify headers are applied:

# Check security headers curl -I https://your-domain.com | grep -E "Strict-Transport|X-Frame|X-Content"
2.6 Dependency Security
# Run npm security audit npm audit # Fix vulnerabilities (review changes first) npm audit fix # For production, ensure no high/critical vulnerabilities npm audit --audit-level=high # Should return "found 0 vulnerabilities"
2.7 Rate Limiting (API Protection)

Add rate limiting to critical endpoints:

# Install rate limiting package npm install @upstash/ratelimit @upstash/redis # Or use Vercel's built-in rate limiting (vercel.json): { "functions": { "app/api/**/*.ts": { "maxDuration": 10 } } }

Critical endpoints to rate limit:

  • Login/signup endpoints
  • Password reset
  • Any endpoint that sends emails
  • Payment/checkout endpoints

PART VII: FILE CONTROL SYSTEM NEW

Artifact Organization for AI-Assisted Development

Chapter 29: Project File Structure

In this chapter, you'll learn the standard file structure for AI-assisted development. This structure enables the MOAI workflow by establishing clear locations for every artifact. By the end of this chapter, your project will be organized for efficient AI-assisted development.

29.1 Why File Control Matters

The File Control System enables MOAI workflow by establishing clear locations for every artifact. When Claude Code or any AI assistant needs to reference your design decisions, architecture, or requirements, it knows exactly where to look. Without this structure:

  • AI assistants can't find your design documents to reference them
  • SPECs reference non-existent Build Contract locations
  • CLAUDE.md can't accurately describe your project structure
  • Test files get scattered, making coverage reports inaccurate

29.2 The Standard Structure

This structure balances simplicity with the needs of AI-assisted development. Every location has a clear purpose, making it easy for both humans and AI tools to navigate.

project-root/ |-- docs/ # Design artifacts | |-- build-contract.md # Bridge document | +-- specs/ # SPEC documents |-- src/ # Application code | |-- app/ # Next.js app router | |-- components/ # React components | +-- lib/ # Utilities |-- src/__tests__/ # Test files |-- supabase/ # Database config |-- CLAUDE.md # AI context file |-- TECH-DEBT.md # Technical debt register +-- README.md

29.5 When to Update Files

Documentation that doesn't evolve with your code becomes misleading. These triggers help you maintain documentation as a habit rather than a chore you forget about.

File Maintenance Triggers

  • CLAUDE.md — Update when: starting new milestone, changing patterns, adding conventions
  • TECH-DEBT.md — Update when: at each checkpoint, after debt review, when debt items resolved
  • Build Contract — Update when: design decisions change, new features added to scope
  • SPEC files — Update when: requirements clarified, test cases added, status changes
  • README.md — Update when: setup steps change, new dependencies added
Keep Documentation in Sync: Outdated documentation is worse than no documentation. When you make significant changes, update the relevant files immediately. Add this to your commit checklist.
