Chapter 19: Multi-Environment Configuration

A proper multi-environment setup is essential for professional SaaS development. This chapter provides a complete guide to configuring three isolated environments: Development, Staging (Preview), and Production.

19.1 Environment Strategy Overview

The three-environment model provides isolation between development work, testing/review, and production users. Each environment connects to its own Supabase project and uses the appropriate Stripe mode.

The Three Environments

Environment Purpose Next.js Supabase Stripe
Local Development Your daily development work Dev server (localhost:3000) Development project (cloud) Test mode
Preview/Staging PR testing, external feedback Vercel preview deploys Staging project (cloud) Test mode
Production Live users, real payments Vercel production Production project (cloud) Live mode

Architecture Diagram

Developer Machine Vercel Preview Vercel Production | | | v v v [Next.js Dev Server] [Preview Deploy] [Production Deploy] | | | v v v [Supabase DEV] [Supabase STAGING] [Supabase PROD] | | | v v v [Stripe TEST mode] [Stripe TEST mode] [Stripe LIVE mode]

Cost Breakdown

Service Free Tier Recommended Setup Cost
Supabase 2 projects free Dev + Staging on Free, Production on Pro $25/mo for Prod (at launch)
Vercel Hobby tier (personal) Hobby for solo, Pro for teams $0-20/mo
Stripe No monthly fee Pay per transaction only 2.9% + 30c per transaction

Why Three Separate Projects?

Three Supabase projects provides complete data isolation. Preview testers don't pollute your development data. Production data is completely separate from test data. This isolation is worth the minor cost increase and prevents data contamination issues that are painful to debug.

19.2 Supabase Project Setup

Create three separate Supabase projects to ensure complete environment isolation.

Step 1: Create Development Project

  1. Go to supabase.com and sign in
  2. Click "New Project"
  3. Name: [project-name]-dev
  4. Database password: Generate a strong password and save it securely
  5. Region: Choose closest to your location (for faster development)
  6. Wait for project to provision (~2 minutes)

Step 2: Create Staging Project

  1. Click "New Project" again
  2. Name: [project-name]-staging
  3. Database password: Generate a different strong password
  4. Region: Same as your production target region (to match behavior)

Step 3: Create Production Project

  1. Click "New Project"
  2. Name: [project-name]-prod
  3. Database password: Generate a different strong password
  4. Region: Choose based on your target users (e.g., us-east-1 for US users)

Step 4: Configure Auth Settings

Repeat for each project. Go to Authentication → URL Configuration:

Project Site URL Redirect URLs
Dev http://localhost:3000 http://localhost:3000/**
Staging https://[project]-*-[username].vercel.app https://*-[username].vercel.app/**
Prod https://[your-domain].com https://[your-domain].com/**

For each project, go to Authentication → Providers and enable your chosen auth methods (Email, OAuth providers, etc.).

Step 5: Enable Row Level Security

Critical Security Requirement

RLS must be enabled on ALL tables in ALL environments. Never disable RLS in production. This is your primary data access control layer.

-- Run this for each table you create ALTER TABLE your_table_name ENABLE ROW LEVEL SECURITY; -- Example: Enable RLS on user_profiles ALTER TABLE user_profiles ENABLE ROW LEVEL SECURITY;

Step 6: Record Your Credentials

From each project's Settings → API, record these values:

Project Project URL Anon Key Service Role Key DB Password
Dev https://[ref].supabase.co eyJ... eyJ... (saved securely)
Staging https://[ref].supabase.co eyJ... eyJ... (saved securely)
Prod https://[ref].supabase.co eyJ... eyJ... (saved securely)

Never Commit Credentials

These values go in Vercel environment variables only. Never commit them to your repository. Add .env.local to your .gitignore file.

19.3 Local Development Setup

Your local development environment connects to the cloud Development Supabase project. This approach is simpler than running Supabase locally via Docker and requires no additional infrastructure.

Prerequisites

  • Node.js 20+ installed
  • npm or pnpm package manager
  • Supabase CLI: npm install -g supabase
  • Vercel CLI: npm install -g vercel
  • Git configured with your credentials

Step 1: Clone and Install

git clone [your-repo-url] cd [project-name] npm install

Step 2: Link to Vercel Project

vercel link # Follow prompts to connect to your Vercel project # Select your team/account and project when prompted

Step 3: Pull Environment Variables

vercel env pull .env.local # This creates .env.local with Development environment variables

Step 4: Verify Connection

npm run dev # Open http://localhost:3000 # Verify auth and database connections work

Step 5: Link Supabase CLI (for migrations)

supabase login supabase link --project-ref [your-dev-project-ref] # Project ref is in your Supabase project URL: # supabase.com/dashboard/project/[ref]

Shared Development Database

Your local development connects to the cloud Development Supabase project. Changes to the database (via the app or migrations) affect this shared environment. If working with a team, coordinate database changes to avoid conflicts.

Local Environment File Template

Your .env.local file (pulled from Vercel) should contain:

# .env.local - DO NOT COMMIT THIS FILE # Supabase (Development) NEXT_PUBLIC_SUPABASE_URL=https://[ref].supabase.co NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJ... SUPABASE_SERVICE_ROLE_KEY=eyJ... # Stripe (Test Mode) NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY=pk_test_... STRIPE_SECRET_KEY=sk_test_... STRIPE_WEBHOOK_SECRET=whsec_... # App NEXT_PUBLIC_APP_URL=http://localhost:3000 # Claude API (if using AI features) ANTHROPIC_API_KEY=sk-ant-...

Local Setup Verification Checklist

Verify Your Local Environment

  • npm run dev starts without errors
  • Can sign up / sign in via the app
  • Database queries return data (check browser console)
  • Stripe checkout opens in test mode
  • AI features work (if applicable)

19.4 Vercel Project Configuration

Vercel hosts your Next.js application and manages environment variables across all three environment scopes.

Step 1: Import Project

  1. Go to vercel.com and sign in
  2. Click "Add New Project"
  3. Import from your GitHub repository
  4. Framework Preset: Next.js (auto-detected)
  5. Root Directory: ./ (unless using monorepo)
  6. Build Command: npm run build (default)
  7. Output Directory: .next (default for Next.js)

Step 2: Understand Environment Scopes

Vercel has three environment variable scopes that map to your environments:

Scope When Used Supabase Project Stripe Mode
Development vercel dev and vercel env pull Dev Test
Preview All preview deployments (PRs, branches) Staging Test
Production Production deployment only Prod Live

Step 3: Add Environment Variables

Go to Project Settings → Environment Variables. Add each variable with the appropriate scope:

Variable Development Preview Production
NEXT_PUBLIC_SUPABASE_URL Dev project URL Staging project URL Prod project URL
NEXT_PUBLIC_SUPABASE_ANON_KEY Dev anon key Staging anon key Prod anon key
SUPABASE_SERVICE_ROLE_KEY Dev service key Staging service key Prod service key
NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY pk_test_... pk_test_... pk_live_...
STRIPE_SECRET_KEY sk_test_... sk_test_... sk_live_...
STRIPE_WEBHOOK_SECRET Local webhook secret Staging webhook secret Prod webhook secret
NEXT_PUBLIC_APP_URL http://localhost:3000 (use VERCEL_URL) https://yourdomain.com
ANTHROPIC_API_KEY sk-ant-... sk-ant-... sk-ant-...

Handling Dynamic Preview URLs

Preview deployments have dynamic URLs. Handle this in your code:

// lib/config.ts export const getAppUrl = () => { if (process.env.NEXT_PUBLIC_APP_URL) { return process.env.NEXT_PUBLIC_APP_URL; } if (process.env.VERCEL_URL) { return `https://${process.env.VERCEL_URL}`; } return 'http://localhost:3000'; };

Step 4: Configure Custom Domain (Production)

  1. Go to Project Settings → Domains
  2. Add your custom domain (e.g., yourdomain.com)
  3. Follow DNS configuration instructions (add CNAME or A record)
  4. HTTPS is enabled automatically

19.5 Preview Deployments with Password Protection

Vercel automatically creates preview deployments for every push. These are useful for PR review and external tester feedback.

How Preview Deployments Work

  1. Push a branch or open a PR
  2. Vercel automatically creates a preview deployment
  3. URL format: [project]-[branch]-[username].vercel.app or [project]-[hash].vercel.app
  4. Preview uses environment variables scoped to "Preview"
  5. Each push updates the same preview URL for that branch

Enable Password Protection

Password protection requires Vercel Pro ($20/mo) or Team plan.

  1. Go to Project Settings → Deployment Protection
  2. Enable "Password Protection" for Preview deployments
  3. Set a password to share with testers
  4. Optionally enable "Vercel Authentication" for team members

When to Use Password Protection

Password protection adds friction but ensures only intended testers access your preview. For development previews you don't share externally, you can skip this. Enable it when you need to share with clients, stakeholders, or external testers.

Sharing Previews with Testers

Preview Sharing Workflow

  • Push your changes to a branch
  • Wait for Vercel deployment to complete (check GitHub status or Vercel dashboard)
  • Copy the preview URL from Vercel dashboard or GitHub PR comment
  • Share URL and password with tester
  • Direct tester to specific flows to test
  • Collect feedback (GitHub PR comments, Slack, email, etc.)

Preview Environment Data

Preview Data Persists in Staging

Preview deployments connect to your Staging Supabase project. Any data created during testing persists in Staging. Periodically reset Staging data if it becomes cluttered:

-- Reset staging data (run in Supabase SQL Editor for Staging project ONLY) -- WARNING: Only run this on STAGING, never on production! TRUNCATE TABLE user_profiles CASCADE; TRUNCATE TABLE subscriptions CASCADE; -- Add other tables as needed

19.6 Stripe Environment Configuration

Stripe provides separate Test and Live modes. Use Test mode for development and staging; Live mode for production only.

Understanding Stripe Modes

Mode API Keys When to Use Real Charges?
Test pk_test_*, sk_test_* Local development, Preview/Staging No (use test cards)
Live pk_live_*, sk_live_* Production only Yes (real money)

Step 1: Configure Test Mode

  1. Go to Stripe Dashboard → Developers → API keys
  2. Ensure you're in "Test mode" (toggle in top-right)
  3. Copy Publishable key (pk_test_...)
  4. Copy Secret key (sk_test_...)

Step 2: Create Test Products and Prices

In Stripe Test mode, create your subscription products:

Product: [Your Product Name] +-- Price: Monthly ($X/mo) -> price_1ABC... +-- Price: Yearly ($Y/yr) -> price_1XYZ...

Test vs Live Products

Test products are separate from Live products. You'll recreate them in Live mode before launch, or use Stripe's "Copy to live mode" feature.

Step 3: Configure Webhooks

You need separate webhook endpoints for each environment:

Environment Endpoint URL How to Configure
Local Via Stripe CLI forwarding See command below
Staging https://[staging-url]/api/webhooks/stripe Stripe Dashboard (Test mode)
Production https://[your-domain]/api/webhooks/stripe Stripe Dashboard (Live mode)

Local Webhook Testing with Stripe CLI

# Install Stripe CLI (macOS) brew install stripe/stripe-cli/stripe # Login to Stripe stripe login # Forward webhooks to local server stripe listen --forward-to localhost:3000/api/webhooks/stripe # This outputs a webhook signing secret (whsec_...) # Use this value for STRIPE_WEBHOOK_SECRET in .env.local

Creating Webhook Endpoints in Stripe Dashboard

For Staging (Test mode):

  1. Go to Developers → Webhooks → Add endpoint
  2. URL: Your Vercel preview URL + /api/webhooks/stripe
  3. Select events: checkout.session.completed, customer.subscription.created, customer.subscription.updated, customer.subscription.deleted, invoice.payment_failed
  4. Copy the signing secret → Add to Vercel Preview env as STRIPE_WEBHOOK_SECRET

For Production (Live mode):

  1. Switch to Live mode in Stripe Dashboard
  2. Go to Developers → Webhooks → Add endpoint
  3. URL: Your production domain + /api/webhooks/stripe
  4. Select the same events as staging
  5. Copy the signing secret → Add to Vercel Production env as STRIPE_WEBHOOK_SECRET

Step 4: Launch Checklist for Stripe

Before Going Live with Payments

  • Create products/prices in Live mode (or copy from Test)
  • Update Production environment variables with live keys
  • Create production webhook endpoint in Live mode
  • Update STRIPE_WEBHOOK_SECRET in Production env
  • Test one real transaction before full launch
  • Configure Stripe Tax if applicable
  • Set up payout schedule and bank account

19.7 Database Migration Workflow

Migrations are version-controlled SQL files that evolve your database schema. Create migrations in development, test in staging, then apply to production.

Setting Up Supabase CLI for Migrations

# Initialize Supabase in your project (if not done) supabase init # Link to your Development project supabase link --project-ref [your-dev-project-ref] # Project ref is found in: supabase.com/dashboard/project/[ref]

This creates a supabase/ directory:

supabase/ +-- config.toml +-- migrations/ | +-- (migration files go here) +-- seed.sql (optional)

Creating a New Migration

# Create a new migration file supabase migration new add_user_profiles_table # This creates: supabase/migrations/[timestamp]_add_user_profiles_table.sql

Edit the migration file with your SQL:

-- supabase/migrations/20240115120000_add_user_profiles_table.sql CREATE TABLE user_profiles ( id UUID PRIMARY KEY DEFAULT gen_random_uuid(), user_id UUID REFERENCES auth.users(id) ON DELETE CASCADE, full_name TEXT, avatar_url TEXT, created_at TIMESTAMPTZ DEFAULT NOW(), updated_at TIMESTAMPTZ DEFAULT NOW() ); -- Enable RLS (REQUIRED) ALTER TABLE user_profiles ENABLE ROW LEVEL SECURITY; -- RLS Policies CREATE POLICY "Users can view own profile" ON user_profiles FOR SELECT USING (auth.uid() = user_id); CREATE POLICY "Users can update own profile" ON user_profiles FOR UPDATE USING (auth.uid() = user_id); CREATE POLICY "Users can insert own profile" ON user_profiles FOR INSERT WITH CHECK (auth.uid() = user_id);

Applying Migrations

To Development (remote)

supabase db push # Applies all pending migrations to your linked (Dev) project

To Staging

Option 1: Link temporarily via CLI

supabase link --project-ref [your-staging-project-ref] supabase db push supabase link --project-ref [your-dev-project-ref] # Re-link to dev

Option 2: Use Supabase Dashboard

  1. Go to Staging project → SQL Editor
  2. Copy migration SQL and run manually
  3. Verify tables created correctly

To Production

Production Migration Safety

Production migrations require extra care. Always create a backup first. Review the migration SQL carefully before applying.

# Create a backup first (Supabase Pro feature) # Go to Project Settings -> Database -> Backups -> Create backup # Option 1: Via CLI (link temporarily) supabase link --project-ref [your-prod-project-ref] supabase db push supabase link --project-ref [your-dev-project-ref] # Re-link to dev # Option 2: Via Dashboard (recommended for production) # Copy migration SQL, review carefully, run in SQL Editor

Migration Best Practices

Migration Checklist

  • Each migration should be atomic (one logical change)
  • Consider rollback strategy for each migration
  • Always enable RLS on new tables
  • Test migration on Dev before Staging
  • Test migration on Staging before Production
  • Create production backup before applying
  • Commit migration files to version control

Handling Schema Drift

If someone makes direct changes via Supabase Dashboard:

# Pull remote schema changes to local migration supabase db pull # This creates a migration file with the differences # Review and commit to version control

Prefer Migrations Over Dashboard Edits

Direct Dashboard edits create schema drift that's hard to track. Prefer using migrations for all schema changes so they're version controlled and reproducible across environments.

19.8 Troubleshooting Common Issues

Issue: "Invalid API key" errors

  • Cause: Wrong Supabase environment variables
  • Fix: Verify you're using the correct project's keys for each environment
  • Check: Ensure NEXT_PUBLIC_SUPABASE_URL matches the expected project

Issue: Auth redirects to wrong URL

  • Cause: Site URL not configured in Supabase Auth settings
  • Fix: Add the deployment URL to Supabase → Authentication → URL Configuration → Redirect URLs
  • For Preview: Add wildcard pattern https://*-[your-vercel-username].vercel.app/**

Issue: RLS blocking all queries

  • Cause: Missing or incorrect RLS policies
  • Fix: Check policies in Supabase → Authentication → Policies
  • Debug: Temporarily use service role key (server-side only) to verify data exists

Issue: Stripe webhooks failing

  • Cause: Wrong webhook secret or URL
  • Fix: Verify STRIPE_WEBHOOK_SECRET matches the endpoint's signing secret
  • Debug: Check Stripe Dashboard → Webhooks → Recent events for error details

Issue: Environment variables not updating

  • Cause: Vercel caches environment variables per deployment
  • Fix: Trigger a new deployment after changing env vars
  • Quick fix: Vercel Dashboard → Deployments → Redeploy

Issue: Preview deployment can't connect to Staging Supabase

  • Cause: Preview environment variables pointing to wrong project
  • Fix: Ensure Preview-scoped variables point to Staging Supabase project URL and keys

Issue: Local development connecting to wrong database

  • Cause: Stale .env.local file
  • Fix: Re-run vercel env pull .env.local to get latest Development variables

PART IV-B: BUILD CONTRACT NEW IN v3.0

Bridging Design to Implementation

Chapter 20: Build Contract Introduction

The Build Contract is a bridge document that compresses your design artifacts (Design Brief, UX Package, UI System, Architecture) into a structured reference optimized for implementation.

Why Build Contract?

Design artifacts are optimized for exploration. But during implementation, you need quick reference to decisions made. The Build Contract extracts the "what" and organizes it for implementation lookup. SPECs reference Build Contract sections rather than hunting through multiple design documents.

Without Build ContractWith Build Contract
SPECs reference multiple documentsSPECs reference single source
~15-20K tokens for design context~2-5K tokens for relevant sections
Inconsistent terminology possibleSingle canonical vocabulary

Chapter 21: Build Contract Structure

Every Build Contract contains seven standard sections:

  1. Vocabulary: Canonical terms used throughout the product
  2. User Model: User types, permissions, authentication, core flows
  3. Screen Inventory: Complete list of screens with routes
  4. Component Specifications: Key component behaviors and states
  5. Data Model: Database entities, columns, types, constraints
  6. API Surface: All API routes with methods and auth requirements
  7. Quality Standards: Code structure, security, testing requirements

Chapter 22: Generating the Build Contract

I need you to generate a Build Contract from my design artifacts. Please analyze the attached design artifacts and create a Build Contract with these sections: 1. **Vocabulary**: Extract all canonical terms from the Design Brief. Format as table: | Term | Definition | Usage Context | 2. **User Model**: Extract user types, auth, and flows from UX Package. 3. **Screen Inventory**: Extract all screens with routes from UI System. Format as table: | Screen | Route | Purpose | Key Components | 4. **Component Specifications**: Extract key component behaviors from UI System. 5. **Data Model**: Extract entities and relationships from Architecture. Format as table: | Table | Columns | Constraints | RLS Policy | 6. **API Surface**: Extract all API routes from Architecture. Format as table: | Route | Method | Purpose | Auth Required | 7. **Quality Standards**: Compile standards from all documents. [Attach: Design Brief, UX Package, UI System, Architecture Document]

You've completed all planning artifacts: Design Brief, UX Package, UI System, Architecture Document, and Build Contract. Now you're transitioning from exploration to implementation. This is the most important setup moment in the entire project.

Chapter 23.3: The CLAUDE.md File

The CLAUDE.md file is Claude Code's primary context file. It tells Claude about your project's architecture, conventions, and quality standards. Without this file, every Claude Code session starts from scratch with no project knowledge.

Why CLAUDE.md Matters

Without CLAUDE.mdWith CLAUDE.md
Claude guesses at conventionsClaude follows your established patterns
You repeat context every sessionContext persists across sessions
Inconsistent code styleConsistent with your standards
No awareness of your architectureKnows your stack, schema, API patterns

CLAUDE.md Template

Create this file at the root of your project:

# CLAUDE.md ## Project Overview [PROJECT_NAME] is a [brief description]. Built with Next.js 14+, Supabase, and Claude API. ## Technology Stack - **Framework**: Next.js 14+ with App Router - **Language**: TypeScript (strict mode) - **Styling**: Tailwind CSS - **Database**: Supabase (PostgreSQL) - **Auth**: Supabase Auth - **AI**: Claude API (Anthropic) - **Payments**: Stripe - **Hosting**: Vercel ## Project Structure ``` src/ ├── app/ # Next.js App Router pages │ ├── (auth)/ # Auth-required routes │ ├── (public)/ # Public routes │ └── api/ # API routes ├── components/ # React components │ ├── ui/ # Base UI components │ └── features/ # Feature-specific components ├── lib/ # Utilities and helpers │ ├── supabase/ # Supabase client and helpers │ ├── stripe/ # Stripe integration │ └── utils/ # General utilities └── types/ # TypeScript type definitions ``` ## Code Standards - Functions: Max 30 lines - Files: Max 200 lines - Nesting: Max 3 levels deep - All functions must have explicit return types - Use Zod for runtime validation - Handle all errors explicitly (no silent catches) ## Database Conventions - Table names: snake_case, plural (e.g., `user_profiles`) - Column names: snake_case (e.g., `created_at`) - All tables have: `id` (uuid), `created_at`, `updated_at` - RLS policies required on all tables ## API Conventions - Routes in `src/app/api/` - Use route handlers (not pages) - Always validate input with Zod - Return consistent JSON: `{ data, error }` ## Key Commands - `npm run dev` - Start development server - `npm run build` - Production build - `npm run test` - Run tests - `npm run lint` - Run ESLint - `npm run type-check` - TypeScript check ## Current Sprint Focus [Update this as you progress through milestones] - Currently working on: M1 - Project Setup - Next milestone: M2 - Design System ## Reference Documents - Build Contract: `docs/build-contract.md` - Architecture: `docs/architecture.md` - SPECs: `docs/specs/`
Keep CLAUDE.md Updated: As your project evolves, update this file. Add new patterns you establish, document decisions, and update the "Current Sprint Focus" section when you change milestones.

Chapter 23.7: Verification Checklist

Before starting Milestone 1, verify your environment is ready:

Environment Ready Checklist

  • Project created: Next.js app with TypeScript, Tailwind, App Router
  • Git initialized: At least one commit with clean working tree
  • CLAUDE.md exists: At project root with your project details filled in
  • TECH-DEBT.md exists: At project root for tracking technical debt (see Chapter 27)
  • docs/ folder exists: Contains build-contract.md at minimum
  • docs/specs/ folder exists: Empty, ready for SPECs
  • Claude Code installed: `claude --version` returns version number
  • Test Claude Code: Run `claude "Read CLAUDE.md and summarize the project"` — it should correctly describe your project

Ready for Build Phase

If all items are checked, you're ready to begin Milestone 1. Open your terminal in the project directory and start Claude Code. Your first task will be writing SPEC-SETUP-001 for project initialization.
