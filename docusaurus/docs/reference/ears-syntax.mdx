## What is EARS?

EARS (Easy Approach to Requirements Syntax) provides five sentence patterns for writing requirements. Each pattern has a specific trigger condition that makes the requirement testable.

The core insight: **every requirement has a condition under which it applies**. EARS makes that condition explicit.

## The Five EARS Patterns

| Type | Pattern | Use When |
|------|---------|----------|
| **Ubiquitous** | The [system] shall [action]. | Requirement always applies |
| **Event-Driven** | When [trigger], the [system] shall [action]. | Triggered by a specific event |
| **State-Driven** | While [state], the [system] shall [action]. | Behavior depends on system state |
| **Optional** | Where [condition], the [system] shall [action]. | Conditional/feature-flagged behavior |
| **Unwanted** | The [system] shall not [action]. | Explicitly forbidden behaviors |

## Ubiquitous Requirements

**Pattern**: `The [system] shall [action].`

Use for requirements that are **always true**, regardless of state or events.

### Examples

```
The system shall encrypt all passwords using bcrypt with a cost factor of 12.

The system shall store all timestamps in UTC format.

The system shall validate email addresses using RFC 5322 format.

The photo upload component shall accept JPEG, PNG, and HEIC image formats.
```

### When to Use

- Security requirements that must always hold
- Data format standards
- Architectural constraints
- Default behaviors

### Common Mistake

Don't use ubiquitous when there's actually a condition:

```
❌ The system shall display the admin panel.
   (Only for admin users!)

✅ Where the user has admin role, the system shall display the admin panel.
```

## Event-Driven Requirements

**Pattern**: `When [trigger], the [system] shall [action].`

Use for requirements triggered by a **specific event** - user action, system event, or external input.

### Examples

```
When the user clicks Submit, the system shall validate all form fields.

When a photo upload completes, the system shall generate a thumbnail.

When the user drops an image on the upload zone, the system shall begin
uploading immediately and display a progress indicator.

When the API returns a 401 error, the system shall redirect to /login.

When the subscription expires, the system shall downgrade the user to
free tier and send an email notification.
```

### When to Use

- User interactions (clicks, form submissions)
- System events (timer fires, upload completes)
- External triggers (webhook received, API response)
- State transitions (user logs in, payment succeeds)

### Writing Good Triggers

Be specific about the event:

```
❌ When the user interacts with the form...
   (Too vague - which interaction?)

✅ When the user clicks the Submit button...
✅ When the user presses Enter in the email field...
✅ When the user tabs away from the password field...
```

## State-Driven Requirements

**Pattern**: `While [state], the [system] shall [action].`

Use for requirements that apply **continuously during a specific state**.

### Examples

```
While photos are uploading, the system shall disable the Generate button
and display "Uploading..." text.

While the user is unauthenticated, the system shall redirect all
protected routes to /login.

While the network is offline, the system shall queue mutations locally
and display an offline indicator.

While the user's subscription is expired, the system shall display
a renewal banner on all pages.
```

### When to Use

- Loading states
- Authentication states
- Subscription tiers
- Feature flags
- Network conditions

### State vs Event

State requirements describe **ongoing behavior**; event requirements describe **one-time responses**:

```
State:  While uploading, disable the button.
        (Continuously true during upload)

Event:  When upload completes, enable the button.
        (Happens once at completion)
```

## Optional/Conditional Requirements

**Pattern**: `Where [condition], the [system] shall [action].`

Use for requirements that only apply under **certain conditions** - feature flags, user types, or configuration.

### Examples

```
Where the user has Pro subscription, the system shall allow up to 50
photos per listing.

Where the user has enabled dark mode, the system shall render all
components with dark theme colors.

Where the feature flag "new-editor" is enabled, the system shall use
the rich text editor instead of plain textarea.

Where the listing has more than 10 photos, the system shall display
them in a paginated gallery.
```

### When to Use

- Feature flags
- Subscription tiers
- User preferences
- A/B tests
- Configuration options

### Optional vs State

"Where" implies a **static condition** (set once, doesn't change during use).
"While" implies a **dynamic state** (can change during use).

```
Where:  Where the user is a Pro subscriber...
        (Subscription tier doesn't change mid-session)

While:  While the upload is in progress...
        (Upload state changes during interaction)
```

## Unwanted Behavior Requirements

**Pattern**: `The [system] shall not [action].`

Use to **explicitly forbid** behaviors - often for security, compliance, or UX constraints.

### Examples

```
The system shall not accept files larger than 10MB.

The system shall not store credit card numbers in plain text.

The system shall not expose user email addresses in API responses
to other users.

The system shall not allow password changes without email verification.

The system shall not display loading spinners for operations
completing under 200ms.
```

### When to Use

- Security constraints
- Size/resource limits
- Privacy requirements
- UX constraints (no flash of content, no layout shift)
- Compliance requirements

### Pair with Positive Requirements

Unwanted requirements are often paired with positive alternatives:

```
The system shall not store passwords in plain text.
The system shall hash passwords using bcrypt before storage.

The system shall not accept files larger than 10MB.
When a file exceeds 10MB, the system shall display an error message
with the size limit.
```

## Combining Patterns

Complex requirements often combine multiple patterns:

```
# Feature: Photo Upload Validation

REQ-001 [Ubiquitous]
The photo upload component shall accept JPEG, PNG, and HEIC formats.

REQ-002 [Unwanted]
The system shall not accept files larger than 10MB.

REQ-003 [Event-Driven]
When the user drops an image on the upload zone, the system shall
validate the file type and size before beginning upload.

REQ-004 [Event-Driven]
When validation fails, the system shall display an error message
specifying the validation failure.

REQ-005 [State-Driven]
While files are uploading, the system shall display a progress bar
and disable the Generate button.

REQ-006 [Optional]
Where the user has Pro subscription, the system shall allow
up to 50 photos per listing.
```

## Converting Vague Requirements

Before EARS:
```
The system should handle errors appropriately.
Users should be able to upload photos.
The app needs to be fast.
```

After EARS:
```
When an API request fails, the system shall display a user-friendly
error message and log the error details to the monitoring service.

When the user clicks the Upload button, the system shall open a file
picker limited to JPEG, PNG, and HEIC formats.

The system shall not display loading indicators for operations
completing in under 200ms.
```

## EARS Checklist

Before finalizing a requirement, verify:

- [ ] **Testable**: Can write a pass/fail test for it
- [ ] **Unambiguous**: Only one interpretation possible
- [ ] **Complete**: Specifies the full behavior
- [ ] **Specific**: No vague words (fast, appropriate, user-friendly)
- [ ] **Follows pattern**: Uses one of the five EARS patterns
